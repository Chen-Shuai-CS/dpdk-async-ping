# "无关帧"是什么：诊断构建的记录

会话 `v4-reboot2` 里有一次 20 秒的运行丢了 1 个请求（`../drift/runs/A-045.json`）。同一次运行里恰好收到 1 个"无关帧"
（既不是 echo reply 也不是 ARP 的帧），之前能逐项核对的两次单个丢包也是这样，于是怀疑无关帧是网络对那个请求回的 ICMP 差错报文。
程序平时只给无关帧计数、不记录内容，这里用一个只用于诊断的构建把内容记下来。解读见 `docs/REPORT.md` §8 末尾。

- **构建**：当前提交加上 `otherlog.diff`（只动冷路径：把无关帧的前 96 个字节、每个超时的 id / seq / T0 记进异常明细，明细上限从 16 条放宽到 256 条）。
  在仓库之外的目录里编译，不进仓库的代码；所以这里的 JSON 里 `git_dirty` 为 true，可执行文件路径也不是 `target/release/`。
- **运行**：同一次开机，2026-10-02 18:26 ~ 20:39 UTC，A，64 session，delay 500 µs，每次 600 秒，共 12 次（第 1 次之后停过十几分钟做别的实验，其余连续）。

46 个无关帧的十六进制原文都在各 JSON 的 `anomalies` 里（每个计数都有对应的一条明细，没有漏记）。逐个解码的结果：

- 全部是 IPv4、目的地址是这张网卡的地址（10.202.15.133），来自 35 个不同的公网源地址；
- 21 个是 ICMP echo request（有人在 ping 这张网卡的公网地址）；
- 25 个是 TCP SYN：16 个指向 22 端口，其余指向 3000 ~ 4001 之间的几个端口（端口扫描）；
- **没有一个是 ICMP 差错报文**（目的不可达、超时之类），也没有别的协议。

**结论**：无关帧是互联网上的背景探测（这张网卡有公网地址；这些帧能到达网卡，说明安全组放行了它们），平均每 2 ~ 3 分钟一个，与我们发出的请求无关。
这 2 小时、8 亿个请求里没有丢包，所以"丢包那一刻收到的无关帧是什么"没有直接看到；
能确定的是：看到的 46 个无关帧没有一个是对我们请求的应答，"无关帧是网络回的差错报文"这个猜测没有得到任何支持。
还解释不了的是：三次能核对的丢包都恰好碰上 1 个无关帧，按现在的到达率（20 秒的运行约 12% 会碰到）纯属巧合的概率不到 1%；
不能排除"公网探测到达"与"丢包"在网关或对端一侧有某种关联，但从本机一侧无法验证。

程序对这些帧的处理是计数后丢弃：不应答公网来的 ping，也不把它们交给任何 session。
