# timer 的"批量唤醒、统一 poll"：对照实验

**来源**：一条外部意见（`docs/REVIEW.md` 第三部分）。收包一侧，reactor 每分发一个包就立刻 poll 它的 task；
timer 一侧不是这样——`Timers::fire`（`crates/rt/src/timer.rs`）先把堆里所有到期的 timer 弹完、wake 完，主循环才 `run_ready` 统一 poll。
而 B 的 `on_timers` 是弹一个、处理一个。意见认为这里也有"批内靠前的被后面的拖慢"的不对称，影响段③（不计分）。

**做法**：不改仓库里的代码，在仓库之外的两个目录里分别编译：

- `Abase`：当前代码（提交 `e3f0cca`），原样编译；
- `Afire1`：同一提交加上 `fire1.diff`——新增 `Timers::fire_one`，主循环改成"触发一个到期的 timer → 马上 `run_ready` → 再触发下一个"，与收包一侧的做法对称；
- `B`：仓库里的 `target/release/raw-ping`，作参照。

三者在同一次开机里轮流跑（`run.sh`），每轮各 60 秒，顺序逐轮轮换，共 6 轮（2026-10-03 02:12 ~ 02:31 UTC）。64 session、delay 500 µs、不导出样本。18 次运行丢包 0、泄漏 0。

**结论**

- **这个不对称是真的，影响的是段③的尾部**：改成"触发一个、poll 一个"之后，段③ p99 平均低约 115 ns（6 轮全部更低），A − B 的段③ p99 从约 +237 变成约 +122。
- **排名指标没有变化**：进程内 p50、p99、段①、慢发送占比都在区间以内；段③ 平均值和三段合计的变化（−5 ns 左右）区间跨过 0。
- **机制没有拆开。** "批内靠前的 task 要等后面的 timer 都被弹出、唤醒"只占几次堆操作的时间，按批的大小（约 86% 的批只有 1 个）解释不了 p99 上百纳秒的变化；
  更可能的是两次发送之间执行的代码变了，上一次发送留下的那段停顿落在了别处（报告 §4 的机制）。这一点没有验证，是推断。
- 两个 A 是两个不同的二进制。同一份代码换一种内存布局，段①能差 5 ns（报告 §3.5），所以几纳秒的平均值差别不能当真；段③ p99 上百纳秒的差别不受这一点影响。

**没有并入正式代码**：它只改善不计分的段③；改 runtime 的调度方式会改变两次发送之间的写入模式，按 v4 第一版的教训（报告 §3.4）需要整套重测，而排名指标不会因此变化。
如果发送由行情触发（段③在关键路径上），它值得做。这一条记在 `docs/DESIGN.md` §1.1 的"还值不值得优化"表里。

文件：`Abase-<轮>.json`、`Afire1-<轮>.json`、`B-<轮>.json`；`fire1.diff` 是实验版的补丁；`run.sh` 是当时的轮流脚本。
