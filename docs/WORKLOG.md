## 2026-09-30 · 01 理解题目与摸底服务器

**怎么想的**
- 题目的核心是 A − B，也就是 async 抽象层的税，而不是 ping 本身快不快。三条硬门槛（10 分钟不崩、零 mbuf 泄漏、零丢包或能自洽解释）任何一条不满足，排名数字就不看。
- 所以优先级是：先保证硬门槛，再保证 A − B 可信（A 和 B 严格对齐），最后才抠纳秒。

**做了什么**
- 通读 SPEC；用 lscpu、ip、ethtool、IMDS 等工具摸清机器配置，只读，没有改任何东西。

**效果 / 发现**
- c8a.xlarge：AMD EPYC 9R45，4 核无超线程，7.6 GiB 内存，AL2023（内核 6.18），东京 apne1-az4。
- 两张 ENA 网卡：
  - device 0：enp39s0，10.202.2.227，SSH 走这张，留给内核和 C；
  - device 1：enp40s0，10.202.15.133，MAC 06:ff:df:7d:66:91，PCI 0000:28:00.0，绑给 DPDK。
- 对端 10.202.8.15 两张网卡都能 ping 通，MAC 与 SPEC 一致。
- 三个对后续影响最大的发现：
  1. 没有 IOMMU 组 → DPDK 只能用 vfio-pci 的 noiommu 模式或 igb_uio。
  2. ENA 在用 LLQ 模式 → DPDK 需要写合并（WC），而主线 vfio-pci 不支持 WC。
  3. 内核 ping 的 RTT 随发包节奏变化很大：连续发约 60 µs，每 200 ms 发一个约 134 µs → 测 C 时节奏必须和 A 可比。
- 系统是裸的：没有 gcc、git、Rust、DPDK，大页为 0，也没有核隔离。

## 2026-09-30 · 07 启动参数（等待重启）

**写入的参数（grubby，全部内核项）**
```
default_hugepagesz=2M hugepagesz=2M hugepages=1024
isolcpus=managed_irq,domain,3 nohz_full=3 rcu_nocbs=3 irqaffinity=0-2 rcu_nocb_poll
nosoftlockup nmi_watchdog=0 tsc=reliable
```
- `isolcpus / nohz_full / rcu_nocbs`：让核 3 几乎只跑 runtime（不被调度其他任务，只有一个任务时不打时钟 tick，RCU 回调挪到别的核）。
- `irqaffinity=0-2` + `managed_irq`：新中断只落在核 0-2，内核托管的中断也避开核 3。
- `rcu_nocb_poll`：RCU 回调线程自己轮询，不再给核 3 发 IPI。
- `nosoftlockup nmi_watchdog=0`：关掉会周期性打断 busy-poll 核的看门狗。
- `tsc=reliable`：关掉 clocksource watchdog 对 TSC 的周期性校验。
- **暂不启用** `idle=poll` 之类的空闲态参数：它会影响核 0-2 上 C（系统 ping）的延迟，属于"C 在什么条件下测才公平"的问题，留到测 C 时再讨论。

**重启前自检**（`check-env.sh`）
- 软件、大页、网卡绑定、irqbalance 全部通过；启动参数类的项要重启后才生效。
- 还有 12 个中断落在核 3，推测是 nvme / ena 这种按 CPU 分配、内核托管的中断，运行时迁不走，重启后由 `managed_irq` 和 `irqaffinity` 处理，**重启后复查**。

## 2026-09-30 · 09 架构设计（写代码之前）

**总原则：A 和 B 除了"有没有 runtime"之外，其他一切共用同一份代码。** 否则 A − B 减出来的就不只是抽象层成本。

**crate 划分（Cargo workspace）**
| crate | 内容 | A 用 | B 用 |
|---|---|---|---|
| `dpdk-sys` | bindgen 生成的裸绑定 + 一个很薄的 C shim（包装 `rte_eth_rx_burst` 等 static inline 函数） | ✔ | ✔ |
| `dpdk` | 安全封装：Eal、Mempool、Mbuf（RAII，Drop 时归还）、Port（rx/tx burst）、TSC | ✔ | ✔ |
| `pingproto` | 帧模板、RFC 1624 增量校验和、reply 解析、ARP 应答；纯 Rust，可以离线单测 | ✔ | ✔ |
| `bench`（实际命名为 **`pingkit`**；TimerHeap 后来单独拆成 **`timerq`**，见 12 条） | 命令行参数、TimerHeap、直方图、报表、housekeeping（ENA watchdog 等） | ✔ | ✔ |
| `rt` | **runtime 本体**：executor、Waker、timer、poll-mode reactor、按 id 分发的信箱 | ✔ | ✘ |
| `async-ping` / `raw-ping` | 两个可执行程序 | A | B |

**已确定的关键设计（附理由）**
1. **发送**：每个包一次 `tx_burst`（1 个包）。T1 的定义就是"tx_burst 返回"，把多个 session 的包攒成一批会让 T1 的语义含糊。先用"分配 mbuf + 拷贝 106B 模板"，简单且显然正确；"每个 session 一个模板 mbuf + refcnt"的优化留作备选。
2. **收包顺序对齐 B**：reactor 每分发一个包，就立刻 poll 被唤醒的 task，而不是先把整批包都分发完再统一 poll。原因：B 天然是"处理一个包、更新一个状态"，A 如果先全部 wake、再统一 poll，第 1 个包的 T3 也要等整批处理完，会人为放大 A − B。
3. **Timer**：用二叉堆（按 TSC deadline 排序）。64 个 session 规模很小，堆的插入是 O(log n) 且精确；时间轮适合海量 timer，这里没有必要。**B 用同一个 TimerHeap 数据结构**（只是不经过 waker），满足 SPEC"B 也要有 timer 路径"的要求。
4. **超时**：不给每个包注册超时 timer（那会带来每包的堆操作和取消成本），而是由 housekeeping 定期扫描 64 个在途 session 的 deadline。A 和 B 用同样的扫描方式。
5. **Waker**：data 里只放 task 编号，wake = 把编号推进固定容量的环形就绪队列（带"已入队"去重位）。clone / drop 都是空操作，没有引用计数。Waker 被规定为 Send + Sync 的问题：wake 时检查当前线程是否是 runtime 所在线程，不是就 abort，保证不会发生数据竞争。
6. **打点**：统一用 `rdtsc`（不加 lfence）。A 和 B 用同一个函数、在语义相同的位置打点。**（后来在 13 条改为 `rdtscp`：rdtsc 的乱序执行会系统性地偏向 B。）**
   - 段③的定义拆成两段：**sleep 误差** = timer 发现到期的时刻 − deadline；**段③** = 发现到期 → 下一个 T0。
7. **统计**：lcore 上用自己实现的对数-线性直方图记录（每次几条指令），在 T3 之后才记录，不进入被测段。进度输出交给核 1 上的上报线程，通过 Relaxed 原子计数读取，lcore 自己不 println。
8. **ENA watchdog**：启动时调用 `rte_timer_subsystem_init()`，housekeeping 里周期性调用 `rte_timer_manage()`；注册 reset 事件回调，出事时干净退出并报告。
9. **零泄漏核对**：mempool 刚创建时（端口启动前）记下 avail；结束时先 drop 所有 task、再 stop 端口（PMD 归还 RX / TX 环上的 mbuf），然后比较 avail 是否等于初值。
10. **链接方式**：用 DPDK 共享库，EAL 会从插件目录自动加载 ENA 驱动，避开静态链接时驱动被链接器丢弃的问题。

**开发顺序**：`dpdk-sys` + `dpdk` 冒烟测试（真网卡上发一个 ping 收到 reply）→ `pingproto` 单测 → `bench` → **B** → `rt` + **A** → 10 分钟长跑 → C → README 与报告。先做 B，因为它既能验证整条硬件链路，又是 A 的对照基线。

## 2026-09-30 · 10 代码：dpdk-sys / dpdk / pingproto / pingkit

**做了什么**
- `dpdk-sys`：bindgen + 一个很薄的 C shim（`rte_eth_rx_burst` / `tx_burst` / `pktmbuf_alloc` / `free` 等都是 static inline，库里没有符号）。
  - 坑：allowlist 写成 `rte_.*` 会把 GTP 等 packed 协议头也拉进来，Rust 报 E0588。**改为只列出实际调用的函数**，生成的绑定从 2 万行降到 2500 行。
- `dpdk`：安全封装，所有 unsafe 都集中在这里，每处都写了 `SAFETY:` 注释。
  - `Mbuf`：RAII，内含裸指针 → 自动 `!Send`。
  - `Mempool`：泄漏为 `'static`，保证 mbuf 不会比池活得久。
  - `RxBurst`：逐个交出所有权，没取走的在 Drop 时释放。
  - `Port`：`!Send + !Sync`；tx 失败时把 mbuf 原样还给调用者。
- `pingproto`：帧模板 + 校验和 + 解析 + ARP。
  - 校验和：启动时对"id / seq / TSC 为 0"的模板预先算好部分和，每个包只加 6 个 16 位字。它与全量重算**逐位相同**（反码加法满足交换律），**20 万组随机数 × 5 种 payload 长度**交叉验证全部一致，所以不存在 RFC 1141 的 0 / 0xFFFF 边界问题。
- `pingkit`（A 和 B 共用）：参数、数据面初始化与零泄漏核对、**发送函数（段①，两边调用同一个函数）**、TimerHeap（二叉堆）、对数-线性直方图（< 256 周期精确，其余相对误差 < 0.8%）、报表、核 1 上的进度线程、周期维护（`rte_timer_manage` + `tx_done_cleanup` + 发布计数）。
  - 查了 ENA 源码：`tx_done_cleanup` 受支持；xmit 只在空闲描述符低于阈值时才顺带回收 → 在维护节拍里主动回收，尽量不让回收落进段①。

## 2026-09-30 · 11 B（raw-ping）首次运行

**设计**：一个 busy-poll 循环分三步：`on_rx`（收包 → 查表 → 就地改状态）→ `on_timers`（到期的 session：record 上一个样本 → 释放 mbuf → 发下一个）→ 每 100 µs 一次 `on_house`（维护、超时扫描、停止判定）。
- reply 的 mbuf 在 sleep 期间由 session 持有，醒来后才 record 并释放（与 SPEC 的 loop 形状一致）。
- 停止：到时间后不再发新请求，等在途请求收到或超时后退出 → 释放所有 mbuf → stop 端口 → 核对 mempool。

**效果（64 session，delay 500 µs，10 s）**
- sent = received = 880,977，0 超时、0 丢包；**mbuf 泄漏 0**（初值 8191，端口启动后 7168，关停后 8191）。
- 进程内耗时：p50 **50 ns**、p99 469 ns、p99.99 1.3 µs、max 39 µs。
  - 段① p50 40 ns / p90 310 ns（**双峰**，待查）；段② p50 10 ns / p99 210 ns。
- 端到端 p50 **245 µs**（!）、速率 8.6 万/秒（理论 11 万/秒）。

**端到端为什么是 245 µs：按 session 数做的对比实验**
| session 数 | 端到端 p50 | 进程内 p50 / p99 |
|---|---|---|
| 1 | 62 µs | 50 / 160 ns |
| 8 | 160 µs | 50 / 401 ns |
| 32 | 107 µs | 50 / 441 ns |
| 64 | 245 µs | 50 / 469 ns |

- 单个 session 时 62 µs，和内核 ping 连续发的 59–63 µs 一致 → **本端的 DPDK 路径正常**。
- RTT 随速率变化且**不单调** → 典型的自适应中断合并（DIM 在几档之间切换）。本端是轮询、没有中断，所以判断发生在**对端内核**。这是 SPEC 说的"不可控因素"，也从实证上说明了排名为什么只看进程内耗时。
- 对 A − B 没有影响（两边面对同样的对端）；但 **C 必须在相同速率下测**，否则对端的状态都不一样。

**其他发现**
- 段①的双峰（40 ns / 310 ns）：单 session 时几乎没有高峰，并发越高越明显。推测是 reply 成批到达 → 多个 session 的 sleep 几乎同时到期 → 同一轮里连续发送，后一次 tx 要等前一次的写合并缓冲 flush / 内存屏障。待查 ENA xmit 源码确认。
- 端口 opackets 恒比我们的 sent 多 106：绑定前内核发出的包，设备计数器未清零。**统计只用自己的计数器**。
- rx_burst 的包数分布：64 session 时 1 个包占 76%，2 个包占 19%，最多 4 个。

## 2026-09-30 · 12 runtime（rt）与 A（async-ping）

**rt 的结构**（crates/rt，约 500 行）
- `executor.rs`：

  - **Waker**：data 里编码 rt_id(16) | 代数(16) | 任务号(32)，clone / drop 是空操作（没有引用计数、没有原子操作）；wake 时通过线程局部变量确认"当前线程正在运行这个 runtime"，否则 abort → 满足 std 对 Waker 的 Send + Sync 约定，不可能发生数据竞争。

## 2026-09-30 · 13 【关键发现】A − B 的 120 ns 里，90% 是测量假象（rdtsc 乱序）

**现象**：A 的段② p50 比 B 多 120 ns。但 put → wake → 入队 → 出队 → poll 应该只有几十条指令。

**先试了 perf，没用上**：`perf record -C 3` 采样 5 秒，样本 55% 落在 `Runtime::run`、27% 落在 `eth_ena_recv_pkts`，几乎全是空转的轮询。真正处理包的路径只占约 1% 的 CPU，而且被内联进了主循环，采样看不出每个包的开销分布。→ **结论：busy-poll 程序不适合用采样型 profiler 定位单包开销，改用精细打点。**

**第一步：把段②拆开**（新增 `probe` 编译特性，默认关闭；executor 在 poll 前打点，driver 在 put 返回后打点）
| 子段（rdtsc） | p50 | p99 |
|---|---|---|
| T2 → put 返回（分类 + 投递 + wake） | 120 ns | 310 ns |
| put 返回 → 开始 poll（回主循环 + 出队） | 10 ns | 10 ns |
| 开始 poll → T3 | 10 ns | 20 ns |
→ executor 本身几乎不花时间；120 ns 全在第一段，但第一段里真正属于 runtime 的只是 put + wake。

**推断**：分类要读网卡刚 DMA 进来的包数据，不在缓存里，一次 cache miss 约 100 ns。B 也读同样的数据，但它的 T3 紧跟在分类之后，只隔几条指令；**rdtsc 不是序列化指令**，乱序执行时可以在 miss 结束之前就被提前执行，于是这 100 ns 被"藏掉"了。A 从分类到 T3 之间有几百条指令，乱序窗口塞不下，rdtsc 只能等 miss 结束。→ 同一把尺子在 A 和 B 上"看到"的东西不同。

**验证**：所有打点改用 `rdtscp`（等前面所有指令执行完、所有读完成才读 TSC；每次约 16 ns，rdtsc 约 8 ns），A 和 B 同时改。
| 指标 | B rdtsc | B rdtscp | A rdtsc | A rdtscp |
|---|---|---|---|---|
| 段② p50 | 10 ns | **120 ns** | 130 ns | 130 ns |
| 进程内 p50 | 50 ns | 180 ns | 170 ns | 180 ns |
| **A − B 进程内 p50** | | | **+120 ns** | **≈ 0 ns** |
- rdtscp 下的 probe：put 返回 → 开始 poll 为 20 ns，开始 poll → T3 为 20 ns，而且其中包含 probe 自己多出的两次 rdtscp。

**结论**
- 如果用天真的测法（rdtsc），报出来的 A − B 是 120 ns，其中 90% 以上是测量假象；**真正的 async 税在 p50 上大约是 10 ns 量级**。
- 决定：**正式版统一使用 rdtscp**（`dpdk::tsc::rdtsc()` 内部实现为 rdtscp，A、B 与 runtime 共用这一个函数）。代价是每个打点多约 8 ns，两边相同。
- 这是"你是否知道税收在哪里"的一个具体答案：**测量工具本身也收税，而且对两边收得不一样**。

**新的疑问（下一步）**

## 2026-09-30 · 14 A / B 交替多轮对比 + 段① 写合并效应

> **更正（见条目 25）**：这一条里"等待发生在驱动的 sfence 上、等写合并缓冲排空"的机制说法已被实验否定。

**A 的 p99 为什么反而更好？按"距上一次发送多久"拆开段①**（20 秒各一轮）：
| 距上次发送 | B 段① p50 / 占比 | A 段① p50 / 占比 |
|---|---|---|
| < 100 ns | **300 ns** / 20% | — / 0% |
| 100–250 ns | **270 ns** / 4% | 60 ns / ≈0% |
| 250–500 ns | 50 ns / 5% | 50 ns / 28% |
| 500 ns–2 µs | 50 ns / 52% | 50 ns / 53% |
| ≥ 2 µs | 50 ns / 19% | 50 ns / 18% |

**机制**（已读 ENA 源码确认，`base/ena_eth_com.c:138`）：每发一个包，先 `wmb()`（x86 上是 sfence），再用 16 次 8 字节写把 128 B 的 LLQ 条目推进写合并内存。sfence 要等上一个包的写合并缓冲排空（实测约 250 ns）。
- 对端的中断合并让多个 session 的 reply 成批到达 → 它们的 sleep 同时到期 → 发送扎堆（两边都有约 80% 的发送距上一次 < 2 µs）。
- B 的循环处理完一个到期的 session 立刻处理下一个，两次发送只隔几十纳秒 → 后一次在段①里等 flush。
- A 的两次发送之间隔着"record + 调度 + poll"（≥ 250 ns）→ flush 在任何被测段之外自然完成。
- **间隔相同时，两边的段①完全一样** → 发送代码确实是对齐的；差别只在"硬件等待被计入了哪一段"。

**结论（写进 README）**：排名指标按原样报告（p50 = 0，p99 = −171），同时给出拆解：
1. runtime 在接收侧真正的税：段② **+10 ns（p50）/ +30 ns（p99）**；
2. 段①的差异来自 ENA 写合并的 flush 等待被归到哪一段，不是 A 更快。
- 考虑过但**没有**做的"修正"：把 B 的发送人为拉开间隔（等于故意拖慢 B），或把多个 session 的包攒成一次 tx_burst（改变了 T1 的语义）。两者都会让 A − B 失去意义。

### 关键发现（答辩重点）
1. **测量工具本身会收税，而且对两边不一样**：用 rdtsc 打点，A − B 的段② 会被报成 +120 ns；改用 rdtscp 后，真实的接收侧税约 +10 ns（13 条）。
2. **ENA 写合并的 flush 约 250 ns**，连续发送时会被计入 B 的段①，所以 A 的 p99 看起来更好；发送间隔相同时两边完全一样（14 条）。
3. **对端的自适应中断合并**让 RTT 随速率非单调变化 → 这说明排名只看进程内耗时是合理的，也说明 C 必须在同速率下测（11、17 条）。
4. **kernel bypass 换来的是确定性**：单路 p99 68 µs 对 281 µs；64 路 p99.99 272 µs 对 4.07 ms；中位数差别不大（17 条）。
5. AWS 会把对端的 ARP 请求转发给我们的网卡（06、16 条）；ENA 的设备计数器不会清零（06、11 条）。

### 尚未解决 / 可以改进
- unexpected reply 的根因未查明，已加明细记录，下次出现时可以分析。
- 段②还能再压：减少 RefCell 借用检查、用泛型存储任务以省掉 vtable、减少线程局部变量访问。接收侧税已约 10 ns，接近测量噪声，优先级低。

- 跨线程 wake → abort 这条路径没有单测（它会杀掉测试进程，需要用子进程来测）。

**速率随对端档位来回切换**（由 速率 = 64 ÷ (RTT + 500 µs) 反推 RTT）：约 8.59 万/秒 → 245 µs，8.77 万 → 230 µs，9.0 万 → 211 µs，9.7 万 → 160 µs，10.4 万 → 115 µs。10 分钟里切换了十几次，100–220 秒之间稳定在 8.77 万/秒。进程内耗时不受影响。

**发现的问题**
1. **【缺陷】解析器不检查源 IP**：异常明细首次抓到了具体内容——`id=16509 超出 session 范围，seq=14618`。我们只用 id 0–63，这个回复不是对我们任何请求的应答。`classify` 只检查"目的 IP 是我"，不检查"源 IP 是对端"，所以任何主机发给我们 IP 的 echo reply 都会进入分发逻辑。
   - 风险：如果这种外来回复恰好带着 0–63 的 id 和某个 session 正在等的 seq，会被**当成那个 session 的回复**，产生一个错误的延迟样本。概率极低，但确实是正确性漏洞。
   - 之前两次 unexpected（A 10 分钟、B 短测）当时没记录明细，很可能是同一类外来包。
2. **【诊断不足】最大值尖刺无法直接归因**：进程内 max 39.9 µs、sleep 误差 max 95.6 µs，我一直说"是虚拟机宿主机借走了 CPU"，但没有直接证据。
3. **【长期运行隐患】直方图计数用 u32**：按 9 万样本/秒、20% 落在同一个桶估算，约 66 小时溢出。10 分钟没有影响。

**可优化之处（按价值排序）**
1. 段①"分配 mbuf + 拷贝 106 B" → 每个 session 预构建一个模板 mbuf + refcnt，省掉分配和拷贝。A、B 同样受益，不改变 A − B。
2. runtime 段②（p50 +10 / p99 +30 ns）：Mailbox / timer 的 RefCell 换成 Cell、同构 session 用泛型存储省掉 vtable。预计只有几 ns，接近测量分辨率，优先级低。
3. 端到端：由对端中断合并决定，不在我们控制范围内。

### 三、排查过程（走过的弯路也记下来）
**(1) 停顿检测器的第一版漏掉了最长的停顿**
- 第一版只统计"没收到包的那一轮"。结果 sleep 误差 max 84 µs，检测到的最长停顿只有 25 µs，对不上。
- 原因：长停顿之后，积压的包立刻被收上来，那一轮被判成"在干活"。
- 第二版分两类：空轮询 > 1 µs；收到包那一轮在取包之前 > 10 µs。先读了 ENA 源码确认：接收环回填只发生在收到包的那次调用里，空轮询不做重活，不会误判。

**(2) 【新发现的缺陷】sleep 误差的最大值一直是启动阶段的假象**
- 第二版检测器下，sleep 误差 max 仍然对不上任何停顿，而且历次运行都稳定在 80 µs 左右。
- 先排除了维护动作：给它计时后，`rte_timer_manage` p50 20 ns / max 3 µs；整个节拍 p99 约 1.3 µs。
- 真正的原因：程序先读时钟作为起点，再创建 runtime、分配直方图、spawn 任务（约 100 µs）。前几个 session 的初始 deadline 在主循环开始转之前就过期了，第一次 sleep 被记成"迟到 80–190 µs"。直方图改成 u64 后初始化变慢，这个值也跟着变大（A 80 → 164–194 µs），反而暴露了它。
- 修复：起点定在"现在之后 1 ms"（`START_LEAD_NS`）。修复后 sleep 误差 max 与最长停顿对上了（B 17.1 对 17.6 µs；A 93.9 对 94.4 µs）。
- **之前把这个 80 µs 归因给虚拟机是错的。**

**(3) A 的段① p99 从 70 ns 变成 150 ns：不是退化，是 p99 卡在悬崖上**
- 现象：改完后 ABBA 里 A 的段① p99 = 150–160（之前 70），进程内 p99 350 → 370。
- 逐项对照实验：
  | 实验 | A 段① p99 | 结论 |
  |---|---|---|
  | 起点延后改回 0 | 70 | 看起来像是"相位"造成的 |
  | 去掉周期性 TX 回收 | p99.9 变成 2.5 µs | 证明周期性回收有价值，但不是原因 |
  | 加无关的诊断指令（起点延后仍为 1 ms），连跑 7 次 | 70–80 | **不是相位**，是极细微的时序差别 |
  | 按"距上次接收环回填多久"分档 | 回填后的发送并不慢 | 否定"回填的寄存器写拖慢 sfence" |
  | T0 之前加 sfence | 尾巴还在 | 否定"record 的直方图写入挂起" |
  | 写包之后加 sfence | 尾巴还在 tx_burst | 否定"写包落在冷缓存行" |
  | 段①拆成 取 mbuf / 写包 / tx_burst | 前两步到 p99.99 都是平的（约 20 ns），尾巴全在 tx_burst | 来自驱动 / 硬件 |
  | 按"发送计数 % 32"统计慢 tx_burst | 集中在余数 3、7、11、…、31（1%–6%），其余约 0.3%；A、B 规律相同 | **网卡 / PCIe 侧的行为** |
- 结论：约 1% 的 `tx_burst` 要 150–270 ns，只与条目在发送队列里的位置有关（每 4 个条目 = 512 B 一次，以 32 个条目 = 4 KB 页为周期起伏）。占比恰好在 1% 上下，所以 p99 读数在 70 和 150 之间跳；所有版本的 p99.9 都是 170–180。
- B 的 p99 变好（521 → 460）是真实的：把 B 每轮循环的两次读时钟合并成一次（与 A 的主循环同构）后，循环更紧凑，同批到期的 session 更多地被拆到相邻两轮，发送间隔拉开，< 100 ns 的发送从 18% 降到 5%。

## 2026-10-01 · 23 讨论：A − B 怎么可能是负数？

> **更正（见条目 25）**：这一条里"等待发生在驱动的 sfence 上、等写合并缓冲排空"的机制说法已被实验否定。
> "负值是记账位置造成的、A 没有更快"这个结论不变；真正的机制是 CPU 的写入队列被上一次发送的门铃写入堵住。

**我的疑问**：A 比 B 复杂，理应多出抽象税；p99 的 A − B 却是 −109 ns，面试官会不会质疑？

**结论：直觉是对的，A 确实更慢；负数只出现在尾部分位数，是一段硬件等待被记到了不同的段里。**

用 10 分钟正式运行的平均值算总账（平均值可以相加，分位数不能）：
| 每个请求的平均耗时（ns） | A | B | A − B |
|---|---|---|---|
| 段① 发送 | 54.2 | 67.9 | −13.8 |
| 段② 接收 | 142.8 | 126.9 | +15.9 |
| 段③ timer 到期 → 下一个 T0（不计分） | 138.3 | 112.8 | +25.5 |
| 排名口径 ① + ② | 196.9 | 194.8 | **+2.1** |
| 自己代码的全部时间 ① + ② + ③ | 335.2 | 307.6 | **+27.5** |

- 抽象税是正的：A 每个请求多约 27.5 ns；排名口径的平均值（+2.1）和 p50（+10）也是正的。
- 尾部为负全部来自段①：网卡写合并缓冲排空约需 250 ns。B 发完一个包立刻发下一个（间隔 < 100 ns 的占 5.3%），后一个包在段①里等；A 两次发送之间隔着调度（本身就超过 250 ns），等待在走到 T0 之前已结束。
- 时间没有省掉，只是换了位置：A 的调度开销在段③（比 B 多 25.5 ns），B 的硬件等待在段①（比 A 多 13.8 ns）。
- 证据：发送间隔相同的各档里，A 和 B 的段① p50 都是 50 ns。
- 比喻：闸机每放行一人要 2.5 秒复位。B 紧跟前一个人冲到闸机口干等；A 路上系了个鞋带，到闸机口正好能过。只统计"在闸机口停留的时间"A 更短，但从出发到通过 A 并不更快。

**答辩时怎么说**
1. 负数只在尾部；p50 +10，平均 +2.1；算上段③，A 每个请求多 27.5 ns。
2. 尾部为负是因为 250 ns 的硬件等待落在 B 的段①、A 的段③；同间隔下两边段①相同（分档表）。
3. runtime 真正的税看段②：p50 +10，p99 +20 ~ +30。

**考虑过但没有做**：在两边的 T0 之前各加一条 sfence，把这段等待都排除在计时之外，p99 的 A − B 会变成约 +10 ~ +30。没做的理由：那是为了让数字好看而改变程序行为；选择两边都按最自然的方式实现、如实报告并拆解。（如果需要，可以做成可选开关，两种口径都报。）

### 二、做的过程中发现的事（审查没有提到）

**发现 1：这台机器的时间戳分辨率是 10 ns。**
- 怎么发现的：给程序加了"启动时标定读时钟成本"，顺手算了相邻读数之差的最大公约数——是 26 个周期，正好 10 ns（TSC 2.6 GHz）。
  再看原始样本：段①、段②全是 26 的整数倍。
- 含义：TSC 读数每 10 ns 才跳一步。之前所有数字都是 10 的整数倍，我一直没有留意。
  "A − B 的 p50 = +10 ns"的准确读法是"差了一格"，真实差值可能是几到十几纳秒。平均值不受影响（量化误差平均掉了）。
- 怎么处理：加了"插值分位数"（把每一格的样本看成均匀分布在格内再插值），Rust 和 Python 各实现一遍，互相核对一致（差 ≤ 0.05 ns）；
  单元测试用模拟的量化时钟验证它确实能还原一格以内的差别，并如实写明在分布的硬边界处误差可到半格。
- 弯路：第一版把直方图的桶映射到格点时用了桶的下界（`lo / step`），而 512 周期以上的桶宽是 4，下界可能比格点小 → 算到上一格去了。
  测试当场抓到，改成"不超过桶上界的最大整数倍"。

**发现 2：之前对"p99 的 A − B 为负"的机制解释是错的（结论没错，机制错了）。**
- 之前的说法：ENA 发包前的 sfence 要等上一个包的写合并缓冲排空，约 250 ns；B 背靠背发送时等在段①里。
- 实验一（T0 前加 sfence）：**毫无变化**。说明等待不是发生在 sfence 上。
- 实验二（T0 前加 mfence）：B 那 5% 的慢发送消失，等待移到段③；A − B 在每个分位数上都变成正的。
- 实验三（T0 前多做 N 次普通内存写入，不带任何栅栏指令）：N ≤ 32 毫无变化，N ≥ 48 效果与 mfence 相同。一个干净的阈值。
- 结论：发送的最后一步是往网卡寄存器写"门铃"，这次写入约 250 ~ 300 ns 才完成；CPU 不等它，后面的写入在 CPU 的写入队列里排队；
  队列填满时 CPU 才停下来。B 两次发送之间写入少，在下一次发送的中途填满（落在段①）；A 多了调度，写入更多，在走到 T0 之前就填满（落在段③）。
- 弯路：实验三的第一版在函数里声明了一个清零的 4 KB 数组，清零本身就是上百次写入，于是 N = 16 也"有效果"，剂量关系是假的。
  看了反汇编才发现；改成不初始化的数组后得到干净的阈值。
- 教训：**没做过实验的话不要写成结论**。"加了 sfence 会怎样"这句话当初是顺手写的推测，审查一追问就露底了。

**发现 3：段①"慢发送"的占比在不同运行之间差别很大。**
同一个二进制重复跑，A 的占比在 0.5% ~ 3.8% 之间，B 在 4% ~ 12% 之间（B 的主要取决于回复扎堆的程度，也就是对端的状态）。
这解释了"段① p99 在 70 和 150 之间跳"：分布是两段式的，p99 落在哪一段只看占比在 1% 的哪一边。
程序现在把这个占比直接报出来。这也说明单次运行的置信区间不够，必须报告多轮之间的波动。

**发现 4：igb_uio 允许两个进程同时打开同一张网卡。** 加了单实例文件锁，故障注入里有对应场景。

**发现 5：段②的 A − B 可以拆成两部分。**
批内第 1 个包（约 78%）的差值约 +10 ns，是 runtime 那条路径本身；每往后一个位置差值再加二十多纳秒，
因为 A 处理完一个包之后的收尾（登记 sleep、存状态、回 executor）比 B 长，会让同一批里后面的包多等。这是下一步优化的方向（没有做）。

**发现 6：满 MTU、1.2 Gbit/s 时有百万分之几十的丢包。**
故障注入的 `payload-1472` 场景里 A 丢了 30 个包。排查：A、B 程度相同；本机网卡的 imissed / ierrors / rx_nombuf / AWS 限额计数全为 0；迟到数为 0；
同样的包速换成 64 字节载荷是 0 丢包，同样的载荷把速率降到 0.4 Gbit/s 也是 0。→ 包在本机之外丢的，与 runtime 无关。
这超出了 SPEC 的工作点，但正好演示"丢包必须能解释"是怎么做的。

**发现 7：mbuf 耗尽时，丢失数与网卡的 imissed 计数对得上**（偶尔 imissed 多 1，是被丢的非 echo 帧）。

### 三、关键发现（更新版，答辩重点）

1. **测量工具本身会收税，而且对两边不一样**：用 `rdtsc` 打点，段②的 A − B 会被报成 +120 ns；改用 `rdtscp` 后约 +10 ns（条目 13）。
2. **时间戳分辨率是 10 ns**：分位数的差值以"格"为单位，一格以内要靠插值；平均值不受影响（条目 25 发现 1）。
3. **p99 的 A − B 为负是记账位置造成的**：发送最后那次门铃写入要 250 ~ 300 ns 才完成，CPU 的写入队列被它堵住，填满时才停。
   B 停在段①里，A 停在 T0 之前。三个实验：sfence 无效 / mfence 有效 / 48 次以上普通写入有效（条目 25 发现 2）。
4. **抽象税是正的，每请求 35 ~ 40 ns**；runtime 路径本身只有约 7.5 ns，其余来自批内排队和调度（条目 25、26）。
5. **样本不独立，运行之间有波动**：对端网卡的中断合并每隔几秒到几十秒换一档；单次运行的置信区间只是下限，要看交替 10 对（条目 25 第五节）。
6. **对端的自适应中断合并**让往返时间随速率非单调变化 → 排名只看进程内耗时是合理的，C 必须在同速率下测（条目 11、17）。
7. **kernel bypass 换来的是确定性**：单路 p99 68 µs 对 148 µs；64 路 p99.99 0.33 ms 对 1.51 ms，max 0.45 ms 对 16.8 ms；中位数差别不大。
8. **每个丢包都要有出处**：对账 → 本机计数器 → 改变一个变量复测。mbuf 耗尽时丢失数与网卡的 imissed 对得上；
   1.2 Gbit/s 时的丢包和 30 分钟里那 1 个丢包，本机计数器全为 0，是在本机之外丢的。

### 七、教训

1. **比较两个版本只能同场配对。** 拿两个会话相减，会把会话之间的波动算成代码的功劳。判断一个改动的收益时，先问"原理上最多能省多少"——超出好几倍就该怀疑比较方法。
2. **"没有再出现"不等于"消失了"，更不等于"修好了"。** 让旧版本也在同样条件下跑一遍，才知道一个现象的消失能不能归功于新版本。
3. **冒烟测试也占时间窗口。** 今天因为先试跑新脚本，正式开始比昨天晚了 5 分钟；如果要研究"开机后头几分钟"，脚本要在重启之前就准备并验证好。
4. 仍然没有回答的：尾部变重的触发条件；开机后头半小时里 v2 是什么样（v2 至今没有在开机后 27 分钟之内跑过）。如果陈帅愿意再重启一次，可以让三者从开机后第一分钟就开始轮流跑。
