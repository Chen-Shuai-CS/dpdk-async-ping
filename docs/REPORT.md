# 延迟报告

> 环境：AWS c8a.xlarge（AMD EPYC 9R45，4 核无超线程），Amazon Linux 2023 / 内核 6.18，DPDK 25.11.3，Rust 1.98.1。
> runtime / 主循环独占被隔离的核 3；打点统一使用 `rdtscp`（TSC 2.600 GHz）；分位数取最近秩，直方图相对误差 < 0.8%（< 98 ns 为精确值）。
> 所有表格由 `scripts/make_report.py` 从 `logs/` 下的 JSON 生成（`<!-- BEGIN:x -->` 与 `<!-- END:x -->` 之间），可复现。
> 本报告的数据全部来自最终代码（2026-10-01）；修复前的运行保留在 `logs/history/`。

## 1. 结论

1. **硬门槛全部满足**：A、B 各连续运行 10 分钟，零崩溃、**零丢包（0 超时）**、**零 mbuf 泄漏**（avail 8191 → 8191），
   AWS 限额计数器无超限。A 共 5461 万个样本，B 共 5418 万个。两条对账（发送侧、接收侧）都为 0。
   超时路径另用 `--timeout-us 150` 做过压力验证：超时数 = 迟到数、对账为 0、零泄漏。
2. **排名指标（进程内耗时 A − B，10 分钟主考核）：p50 = +10 ns（180 对 170），p99 = −109 ns（360 对 469）。**
   ABBA 交替 3 对 × 60 秒的各轮中位数得到同样的结果（+10 / −109）。
3. **税收在哪**：
   - **段②（接收侧：put → wake → 就绪队列 → 出队 → poll → 恢复）是 runtime 真正的税：p50 +10 ns，p99 +20 ~ +30 ns。**
     段②的大头（约 100 ns）是读包数据的 cache miss，A 和 B 都要付。
   - **段①（发送侧）两边执行的是同一个函数**，p50 相同（50 ns）；尾巴来自网卡而不是 runtime（§5）。
     p99 上 A 比 B 小 250 ns，是因为 B 连续处理到期 session 时发送间隔常小于 250 ns，要在段①里等上一个包的写合并缓冲排空；
     A 的两次发送之间隔着一次调度，等待落在被测段之外。**发送间隔相同时两边的段①相同**（§2 的分档表）。
     所以 p99 为负不代表 runtime 比手写循环快。
4. **测量方法是本题的一部分**，有三处如果不处理，报出来的数字就是错的：
   - 用非序列化的 `rdtsc` 打点，A − B 的段② p50 会被报成 +120 ns（B 的读包 cache miss 被乱序执行"藏掉"）→ 统一用 `rdtscp`；
   - 把运行起点取在准备工作之前，sleep 误差的最大值会多出 80–190 µs 的启动假象 → 起点定在启动后 1 ms；
   - 段①的 p99 恰好落在"约 1% 的慢 `tx_burst`"的悬崖边上（§5），读数会在 70 与 150 ns 之间跳 → 要和 p90、p99.9、分档表一起看。
5. **kernel bypass 的收益（A 对 C，同一对端、同样的帧）**：
   - 单路低速率：p50 **63.6 对 82 µs**，p99 **68 对 148 µs**，max 0.14 对 0.65 ms。
   - 64 路同速率：p50 相近（189 对 171 µs，中位数由对端网卡的自适应中断合并决定），但 **p99 197 对 441 µs，p99.99 0.33 对 1.51 ms，max 0.37 对 16.8 ms**。
   - kernel bypass 换来的主要不是中位数，而是**确定性**：本端没有中断、没有空闲态唤醒、没有调度。
6. **timer**：sleep 误差 p50 10 ns、p99 300–350 ns（上限由主循环一轮的时长决定）；段③（发现到期 → 下一个 T0）A 为 70 / 730 ns，B 为 60 / 420 ns，
   差值就是 timer 唤醒路径上的 wake + 调度 + poll。"deadline → 下一个 T0"（另一种读法）A 为 70 / 809 ns，B 为 70 / 681 ns。
7. **异常都能解释**：
   - 最大值尖刺（几十到一百多微秒）：主循环的停顿检测显示 A、B 都是约每秒 216 次被外部打断（累计占 0.064%，平均 3 µs，最长约 150 µs），
     sleep 误差与进程内耗时的最大值都落在其中最长的一次之内 → 来自虚拟机宿主机。
   - 1 个外来 echo reply：来自公网地址 13.214.173.166（id=16509，不是我们的 session），经这张网卡的公网 IP 进来，属于互联网背景流量；已识别并丢弃。

### 总账：为什么 p99 的 A − B 是负的，而抽象税其实是正的

A 做的事比 B 多，总耗时也确实更多；尾部分位数为负，是因为一段硬件等待在两边被记进了不同的段。

**起因**（两个 session 同时到期时，两边的处理顺序不同）：

```text
对端的中断合并把多个 reply 攒成一批送回
        │
        ▼
这几个 session 的 sleep 几乎同时到期 → 要连续发两个包
        │
        ├── B：发完第一个，循环立刻处理第二个（间隔 < 100 ns）
        │       └─▶ 第二个包在【段①】里等网卡排空 ─▶ 段① ≈ 300 ns（计分）
        │
        └── A：发完第一个，先回 executor 调度下一个 task（本身就 ≥ 250 ns）
                └─▶ 等待在走到 T0 之前已经结束，落在【段③】─▶ 段① ≈ 50 ns（段③ 不计分）
```

**同一时刻两边各在做什么**（示意，1 个字符 = 10 ns；pkt1 / pkt2 是连续要发的两个包）：

```text
ns          0    50   100  150  200  250  300  350  400
            |----|----|----|----|----|----|----|----|
NIC              [== draining pkt1, ~300 ns ==]

B  pkt1     [###][...]
B  pkt2               [~ wait for NIC 250 ns ~][###]
                      ^T0                           ^T1
                      |<------ seg1 = 300 ns ------>|   <- ranked

A  pkt1     [###]
A  sched         [. executor > poll > record .]         <- seg3, NOT ranked
A  pkt2                                        [###]
                                               ^T0  ^T1
                                               |<-->|   <- seg1 = 50 ns, ranked

[###] tx_burst    [...] record / scheduling    [~~~] blocked, waiting for the NIC
```

两边的第二个包都在约 400 ns 时交给网卡，A 并没有更快；区别只是这 300 ns 在 B 那边算进了段①（计分），在 A 那边算进了段③（不计分）。

**总账**（用平均值算：平均值可以相加，分位数不能）：

- **抽象税是正的**：算上不计分的段③，A 每个请求比 B 多约 27 ns；排名口径（① + ②）的平均值和 p50 也是正的。
- **只有尾部分位数为负，且全部来自段①**。两边的段①是同一个函数；差别在于网卡写合并缓冲的排空（约 250 ns）被记到了哪一段：
  B 发完一个包立刻发下一个（间隔 < 100 ns 的发送占 5.3%），后一个包要在段①里等前一个包排完；
  A 的两次发送之间隔着"回到 executor → 取任务 → poll → record"，这些调度本身就超过 250 ns，等待在走到 T0 之前已经结束。
- **时间没有被省掉，只是换了位置**：A 的调度开销落在段③（平均比 B 多 25 ns），B 的硬件等待落在段①（平均比 A 多 14 ns）。
- **证据**：上面的分档表里，发送间隔相同的各档，A 和 B 的段①完全相同（p50 都是 50 ns）。
- 可以在两边的 T0 之前各加一条 sfence，把这段等待都排除在计时之外，那样 p99 的 A − B 会变成约 +10 ~ +30 ns。
  没有这样做：那是为了让数字好看而改变程序行为；这里选择两边都按最自然的方式实现，如实报告并给出拆解。

## 6. 怎么读这些数字

1. **排名指标 A − B**：p50 为 +10 ns，p99 为负。负值来自段①的写合并等待被计入哪一段（结论 3），不代表 runtime 更快。
   runtime 自身的税看段②：p50 +10 ns，p99 +20 ~ +30 ns。
2. **与修复前的数字相比**（`logs/history/`，当时 A − B 的 p50 / p99 是 0 / −171）：A 没有变（180 / 350–360）；
   B 变好了（180 / 521 → 170 / 469），因为把 B 每轮循环的两次读时钟合并成了一次（与 A 的主循环同构），
   循环更紧凑后，同一批到期的 session 更多地被拆到相邻两轮处理，间隔 < 100 ns 的发送从 19% 降到 5%。
3. **端到端主要由对端决定**：对端网卡驱动的自适应中断合并让 RTT 随速率非单调变化
   （1 路约 63 µs、64 路 160–245 µs，同一次运行里也会换档）。这部分不受我们控制，也是排名只看进程内耗时的原因；比较 A 与 C 时必须在相同速率下进行。
4. **sleep 误差与段③的 A − B**：p50 相同；A 的 p99 多约 300 ns，是 timer 到期后"wake → 就绪队列 → poll → 走到 send()"这条路径，
   以及同一轮里多个 timer 同时到期时排在后面的 task 要等前面的 task 执行完。它不计入排名指标。
5. **max**：单个样本，由虚拟机宿主机的偶发停顿决定（结论 7）；看 p99.99 更有意义。
6. **样本在 sleep 之后记录**：按 SPEC 的 loop 形状，reply 的 mbuf 在 sleep 期间被持有，醒来后才 `record` 并释放。
