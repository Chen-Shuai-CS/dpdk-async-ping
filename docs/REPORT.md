# 延迟报告

> 环境：AWS c8a.xlarge（AMD EPYC 9R45，4 核无超线程），Amazon Linux 2023 / 内核 6.18，DPDK 25.11.3，Rust 1.98.1。
> runtime / 主循环独占被隔离的核 3；打点统一使用 `rdtscp`（TSC 2.600 GHz）；分位数取最近秩，直方图相对误差 < 0.8%（< 98 ns 为精确值）。
> 所有表格都由 `scripts/report.py` 从 `logs/` 下的 JSON 生成，可复现。

## 1. 结论

1. **硬门槛全部满足**：A、B 各连续运行 10 分钟，零崩溃、**零丢包（0 超时）**、**零 mbuf 泄漏**（avail 8191 → 8191），
   AWS 限额计数器无超限；A 共 5393 万个样本，B 共 5490 万个样本。超时路径另外用 `--timeout-us 150` 做过压力验证：超时数 = 迟到数、对账为 0、零泄漏。
2. **排名指标（进程内耗时 A − B，10 分钟主考核）：p50 = 0 ns（180 对 180），p99 = −171 ns（350 对 521）。**
   另外两次 ABBA 交替（3 对 × 30 秒、3 对 × 60 秒）的中位数得到同样的结果：p50 为 0，p99 约 −170。
3. **税收在哪**：
   - **段②（接收侧：put → wake → 就绪队列 → 出队 → poll → 恢复）是 runtime 真正的税：p50 +10 ns，p99 +30 ns。**
     用 probe 拆开看：put 返回 → 开始 poll 约 20 ns，开始 poll → 恢复约 20 ns（各自都含一次约 16 ns 的 rdtscp 探针）；段②里的大头是"读包数据的 cache miss"，A 和 B 都要付。
   - **段①（发送侧）两边调用的是同一个函数**，p99 却差了 260 ns。原因是 ENA 写合并的 flush 等待（约 250 ns）被计入了哪一段：
     B 有 22.5% 的发送与上一次间隔不到 250 ns，这些发送的段① p50 是 300 ns；A 的两次发送之间天然隔着一次调度，间隔几乎从不低于 250 ns（5393 万次里只有 155 次）。
     **在相同的发送间隔下，两边的段①完全相同**。所以 p99 为负并不代表 runtime 比手写循环快。
4. **测量方法本身是本题的一部分**：如果用非序列化的 `rdtsc` 打点，A − B 的段② p50 会被报成 +120 ns，
   其中约 110 ns 是 B 的读包 cache miss 被乱序执行"藏掉"了。本报告统一使用 `rdtscp`。
5. **kernel bypass 的收益（A 对 C，同一对端、同样的帧）**：
   - 单路低速率：p50 **63 对 74 µs（−11 µs）**，p99 **68 对 281 µs（−213 µs）**，p99.99 94 对 439 µs。
   - 64 路同速率：p50 相近（190 对 182 µs，中位数由对端网卡的自适应中断合并决定），但 **p99 197 对 464 µs，p99.99 272 µs 对 4.07 ms**。
   - kernel bypass 换来的主要不是中位数，而是**确定性**：本端没有中断、没有空闲态唤醒、没有调度。
6. **timer**：sleep 误差 p50 10–20 ns、p99 280–481 ns（主循环一轮的时长决定上限）；段③（发现到期 → 下一个 T0）A 的 p50 / p99 为 70 / 721 ns，
   B 为 50 / 380 ns，差值就是 timer 唤醒路径上的 wake + 调度 + poll。

## 5. 怎么读这些数字

1. **排名指标 A − B**：p50 基本为 0，p99 为负。负值不代表 runtime 比手写循环快，而是来自段①的写合并效应（见下条）。
   runtime 在接收侧真正的税看段②：p50 约 +10 ns，p99 约 +30 ns。
2. **段①的写合并效应**：ENA 每次发送前的 sfence 要等上一个包的写合并缓冲排空（约 250 ns）。
   B 连续处理到期的 session，发送间隔常小于 250 ns，这部分等待被计入 B 的段①；
   A 的两次发送之间隔着调度，等待在被测段之外完成。**在相同的发送间隔下，两边的段①完全相同**（见 §2 的分档表）。
3. **rdtsc 与 rdtscp**：用非序列化的 `rdtsc` 打点，A − B 的段② p50 会是 +120 ns；
   其中约 110 ns 是 B 的读包 cache miss 被乱序执行"藏掉"了。本报告全部使用 `rdtscp`。
4. **端到端主要由对端决定**：对端网卡驱动的自适应中断合并让 RTT 随速率非单调变化
   （1 路 62 µs、8 路 160 µs、32 路 107 µs、64 路 160–245 µs，且每次运行可能落在不同的档位）。
   这部分不受我们控制，也正是排名只看进程内耗时的原因；比较 A 与 C 时必须在相同速率下进行。
5. **unexpected（对不上的 echo reply）**：10 分钟的 A 出现 1 个，另有一次 B 短测出现 1 个；它们不属于任何在途或已超时的请求，
   不影响 sent = received + timeouts 的对账。出现次数与运行时长无关，不像随机重复包；已加入明细记录（`Stats::note_anomaly`），之后的运行会在报告末尾列出 id / seq / 当时 session 的状态。
6. **max 与 p99.99 之后的尖刺**：几十微秒级的孤立尖刺在 A、B 中以相近频率出现，与虚拟机的宿主机活动一致
   （核 3 已隔离，busy loop 下实测每秒仅约 2 次中断）。
7. **样本在 sleep 之后记录**：按 SPEC 的 loop 形状，reply 的 mbuf 在 sleep 期间被持有，醒来后才 `record` 并释放。
