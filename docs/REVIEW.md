## 逐条说明

### R1：在请求完成之前核对回复的身份

**核对结果。** 属实。A 和 B 都是 `id/seq` 一对上就把请求算作完成（`received` 加一、结束等待），sleep 之后才核对回带的时间戳；对不上时只是不记样本。
`seq` 是 16 位，每个 session 约 43 秒回绕一次，所以一个迟到很久或被重放的旧回复理论上能"冒领"当前请求——之后真正的回复会被判成"对不上号"，或者一直不来也不再按原请求超时。
这不是纯理论：测量期间两次云平台事件里各有上千个回复被重放（`HISTORY.md` 第 4 节），当时没有错配只是因为重放发生在几十毫秒之内。

**怎么改的。**
- 判定抽成一个 A、B 共用的函数 `pingkit::matching::judge`：输入"在等的 (seq, T0)"和"到达的 (seq, 回带的时间戳)"，输出 `Accept / TscMismatch / Late / Unexpected`。
- 只有 `Accept` 才结束等待。`TscMismatch` 的包被计数、释放，**不动在途请求，也不动它的超时时刻**。
- 判定发生在 T2 → T3 之内（段②），没有把它挪到计时之外。A、B 各多一次 8 字节的比较。

**统计口径的变化。** `tsc_mismatch` 的含义变了：以前是"已计入 `received` 但不进延迟分布的回复"，现在是"被拒绝的回复"，是收包对账里单独的一类。
- 收包对账：`rx = received + late + unexpected + foreign + tsc_mismatch + other + arp`（多了一项）。
- 样本数 = `received`（以前是 `received − tsc_mismatch`）。
- 新增 `record_mismatch`：sleep 之后的二次核对不符的次数，应恒为 0（见下一段）。

**对性能的影响，以及一次走了弯路的经过。** 第一版（`1da94bf`，标签 `v4-first`）在把核对提前的同时，删掉了 sleep 之后原有的那次核对。
同场对比发现 A、B 的慢发送占比都升高了（A 约 0.3% → 2% ~ 10%，B 约 3% → 11% ~ 20%），进程内 p99 各高了约 60 ns；段②本身没有变化。
用二分法定位（`logs/r1-bisect/`）：原因不是新加的比较，而是被删掉的那次调用——它位于"上一次发送"与"下一个 T0"之间，少了它，上一次发送留下的那段约 250 ns 的停顿就更多地落进计分的段①（报告 §4 的机制）。
最终版（`456aab2`）保留了那次核对，作为第二道、独立的检查（接收侧用 driver 记下的 T0，这里用 session 自己记下的 T0）。
最终版与 v3 的同场配对（6 轮，A、B 各两个版本轮流，报告 §3.4）：A 的段② −1.1 ns（95% 区间 −4.6 ~ +2.5），进程内 p50 −0.8 ns、p99 −3.0 ns；B 的段② +0.4 ns，进程内 p50 +0.1 ns、p99 −6.9 ns；A − B 的 p50 从 +10.0 变成 +9.1。都没有可测出的差别。

**验证。**
- `pingkit::matching`：判定表；匹配时不去查超时历史（2 个测试）。
- `async-ping/src/driver.rs` 与 `raw-ping/src/main.rs`：同一组四个场景、同一组预期（各 4 个测试）——错包先到再来正确的包；错包先到而正确的包一直不来（按原定时刻超时，之后才到的算迟到）；seq 回绕后的旧回复；什么都对不上的回复。
- 实机：v4 的全部运行里 `tsc_mismatch` 与 `record_mismatch` 都是 0，两条对账为 0。

**剩余限制。** 状态转换是在 session 的协议状态上做的单元测试，没有做实机的异常包注入：对端是一台普通主机，不受我们控制；从本机另一张网卡伪造对端地址发包会被 AWS 的源地址检查丢弃。

### R2：让发送重试响应停止条件

**核对结果。** 属实。A 的 `send()` 在发送失败时 sleep 1 µs 后无限重试，循环里不看停止标志；而 A 只有在所有 session 结束后才退出。发送持续失败时，duration 到期或 SIGINT 都不能让它退出；故障恢复之后还可能在停止阶段多发一个请求。B 在每次发送前检查，没有这个问题。

**怎么改的。** `send()` 的返回值改为 `Option<Stamp>`：重试等待之后检查停止标志，已停止则返回 `None`（"没有发出去"），session 直接结束。检查只在重试分支里——第一次尝试之前，session 的循环条件刚检查过——所以正常路径不多一条指令。

**验证（都是本次新执行的）。**
- **修复前复现**：把这三行去掉、用带故障钩子的构建运行（发送从第 2 秒起一直失败，设定 4 秒）：启动 14 秒后进程仍在，SIGINT 4 秒后仍在，只能 SIGKILL。
- **修复后**：五个场景，A、B 各跑一次，10 项全部通过：发送从第 2 秒起一直 `TxFull` / 一直 `NoMbuf`，都在设定的 4.00 秒结束；发送一直失败时 SIGINT，0.02 秒后退出；发送在第 2 ~ 8 秒失败而 duration 是 4 秒，4.00 秒结束、不等恢复；从一开始就发不出去，`sent = 0` 时报告照常生成。每一项都核对零泄漏、两条对账为 0、退出码 0。
- **收尾时限**：停止之后，已经发出去的请求等到回复或各自的超时（默认 10 ms）为止，然后输出统计、核对 mbuf。

**剩余限制。** 故障钩子（`BQ_FAULT_TX`）由 cargo 特性 `fault` 控制，正式的可执行文件里没有这段代码；被测的重试与停止逻辑在两种构建里是同一份源码。没有在真实的"链路中断导致 TX 环永久不动"的情况下测过，那种情况在这台机器上无法人为制造。

### R3：验收脚本必须检查真实退出码

**核对结果。** 属实。原来用"输出里没有匹配到错误字样"当作成功：没有 cargo 时 `command not found` 不匹配任何模式；测试那一项的模式连"编译失败"都匹配不到。

**怎么改的。** `cargo clippy --release --workspace --all-targets -- -D warnings` 与 `cargo test --release --workspace` 都直接看退出码；测试只运行一次，保留那一次的输出，数出来的个数只用于展示。
"不得出现某种内容"类的检查改用 `no_match`：grep 自己出错（文件不存在等）也判为未通过。每一节的标题注明是"本次重新执行"还是"检查已有的日志"。

**验证（本次新执行）。** `scripts/check-compliance.sh --self-test`：命令成功、命令失败、命令不存在、输出全是 ok 但退出码非 0、输出没有错误字样但退出码非 0、输出有 warning 字样但退出码为 0，以及 `no_match` 的三种情况，9 项判定全部符合预期。
另外在去掉 cargo 的环境里实际运行了整个脚本：构建、Clippy、测试三项如实判为未通过。

### R4：补齐 DPDK 安全封装的必要约束

**核对结果。** 四点都属实，是封装边界的问题；正常的应用路径没有触发过。

| 缺口 | 处理 |
|---|---|
| `create_pktmbuf_pool` 的 SAFETY 依赖"EAL 已初始化"，但签名不要求凭证 | 签名增加 `&Eal` 参数 |
| 同一个端口号可以领出多个 `Port` | `configure` 独占领取端口号，`close` 成功后归还；重复领取返回错误 |
| `close(self)` 假设端口已停止 | `Port` 自己记着是否已启动，`close` 会先停止 |
| `stop` 之后仍能通过安全方法调用 `rx_burst` / `tx` | **没有加运行时判断，以 DPDK 的保证 + 实测代替**（见下） |

**关于最后一项。** 端口不在运行状态时，DPDK 的 ethdev 层把它的收发函数指针换成返回 0 的空函数（`eth_dev_fp_ops_reset`，21.11 起；本项目用的 25.11.3 见 `lib/ethdev/ethdev_private.c`）。
所以未启动或已停止的端口上 `rx_burst` 返回 0，`tx` 把 mbuf 原样还给调用者，不会访问已释放的队列。这个前提写进了 `Port` 的类型说明。
没有用运行时判断来保证，是为了不在收发热路径上多一次分支；没有用类型状态（配置态 / 运行态 / 停止态各一个类型），是因为它要改动 runtime 与两个客户端里所有用到 `&Port` 的签名，对本题而言改动面偏大。

**验证（本次新执行）。** `crates/dpdk/tests/lifecycle.rs`，用 DPDK 自带的虚拟网卡 `net_null`，不需要真网卡和 root，在 `cargo test` 里执行：重复领取被拒绝；未启动时收发（收到 0 个，发送被拒绝且 mbuf 还回来）；启动后正常收发；停止后收发；未停止就关闭（`close` 先停止）；全程 mempool 的可用数回到初值。

**剩余限制。** 实测用的是 `net_null` 而不是 ENA；"空函数"的保证来自 ethdev 公共层，与具体驱动无关，但没有在 ENA 上单独做这组非法顺序的测试。没有 `close` 就被丢弃的 `Port` 不归还端口号（那个端口仍处于已配置状态，拒绝再次领取是安全的一侧）。

### R5：实测 C 的速率，并限定 A / C 比较的结论

**核对结果。** 属实，而且在已有的日志里找到了实证：名义 60 秒的 ping，自己报告的实际时长是 62.2 秒；按名义时长算出来的 64,000 包/秒，实测是约 61,900 包/秒（低 3.3%）。

**怎么改的。**
- `scripts/summarize_c.py` 从每个 ping 进程的结尾行（`… time 62200ms`）取它实际跑了多久，逐路算出实际速率再相加；同时记录名义速率、每一路实际时长的最小 / 中位 / 最大、整批从启动到全部退出的墙上时间。
- `scripts/campaign.sh` 先测 C，再给 A / B 选 delay，使它们的**实测**速率对齐 C 的实测速率（先试跑 10 秒量一次，再修正一次）。报告 §6 的每一行都有"实测速率"。
- README §4.5 写明：A 是闭环负载（收到回复后等 delay 再发），C 是开环负载（按固定间隔发）；即使平均速率对齐，相位、批量和在途请求数的分布也不同，所以 A 与 C 的差值不能全部归因于"有没有绕过内核"。

**验证。** 报告 §6（本次新测的一组 A / C 对比）。逐包的原始输出压缩后留在考察机本地（`logs/tmp/c-raw-*.tar.gz`，不进仓库）。

### R6：限制插值分位数的适用范围

**核对结果。** 属实。按格点插值的前提是"桶宽不超过时钟步长"（本机即 4096 周期 ≈ 1.6 µs 以内的值），但 JSON 里对端到端延迟也输出了插值字段，那里桶宽约 790 ns，结果会偏到桶的上界附近。
报告里端到端延迟用的是普通分位数，插值只用于进程内耗时、段①、段②（都在窄桶范围内），所以没有错误的数字流出去；但字段本身是错的。

**怎么改的。** `Hist::quantile_interp` 按桶宽分两种情况：窄桶沿用原来的按格点插值（结果与修改前逐位相同）；宽桶只在桶 [lo, hi) 内线性插值，并夹在 [min, max] 内，精度就是桶宽。函数注释写明了两种情况的误差模型，以及"小数位数不代表测量精度"。

**验证（本次新执行）。** 新增 3 个单元测试：审查方给的算例（所有样本都是 262,158 周期 → 结果恰为 262,158）与宽桶内的均匀分布；窄桶 / 宽桶的分界（4096 周期）；长尾混合分布（主体的分位数不受尾巴影响，尾部的分位数落在尾巴所在的桶里）。原有的"模拟 10 ns 步长"的测试不变并通过。

## 修复后的运行

审查方建议的顺序与实际做法：

1. 逐项确认并修正：见上。
2. 回归测试：`cargo test --release --workspace` 50 个（原 35 个），Clippy `-D warnings` 通过。
3. 短时实机收发：A、B 各 60 秒（README §6.1 贴的就是这一次的输出），零丢包、零泄漏、两条对账为 0。
4. 正式验证：由同一个干净的提交（`e50c0f8`，代码与标签 `v4` 相同）构建 A / B，诊断开关关闭，重新跑了整套（10 分钟主考核、交替 10 对、诊断口径、与系统 ping 的对比、故障注入、30 分钟 × 2、probe）。
   结果是 `logs/` 里现在的这一套，报告是 `docs/REPORT.md`：主考核、30 分钟、交替对比等 43 次运行全部零丢包、零泄漏；故障注入 25 个场景 × A / B 共 50 项通过；合规检查 32 项通过。
   故障注入的第一遍是 49 / 50：`mbuf-exhaust` 的预期"每一个丢失都在网卡的 `imissed` 里"过强——丢得多的时候有约 2% 不在任何网卡计数器里。查过之后把预期改成如实陈述，重跑 50 / 50（报告 §8）。
5. 性能变化的判断：用同场配对（`scripts/versions-ab.sh`，报告 §3.4），没有拿不同时段的数字直接相减。
6. A / C 对比：见 R5。
7. 报告、README 首页的结果、构建版本、日志路径都已与这一套数据对齐。仓库里只保留这一套；v1 ~ v3 的日志保存在考察机本地，结论摘要在 `docs/HISTORY.md`。

**后来补做的**：在 v4 上重启两次，各做了一个复测会话（各 200 次运行；报告 §3.5）。结论的方向在三次开机里一致；
复测里另外发现同一份二进制换一个文件实例、A 的发送段会整体差 5 ns，p50 的差值因此应当读作 +10 ~ +17 ns。
