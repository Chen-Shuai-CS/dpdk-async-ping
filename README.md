# dpdk-async-ping

用 Rust 写的**单核、kernel-bypass 的 async runtime**（`crates/rt`），以及跑在它上面的 ICMP ping 客户端。
自研 executor / Waker / TSC timer / DPDK poll-mode reactor，不依赖任何现成 runtime。

| 标签 | 程序 | 说明 |
|---|---|---|
| **A** | `async-ping` | 跑在 `rt` 上，64 个 session 各是一个独立的 async task |
| **B** | `raw-ping` | 行为完全相同，手写 busy-poll 循环 + 状态表，不经过 runtime |
| **C** | 系统 `ping` | 走内核网卡，作为"不做 kernel bypass"的参照 |

64 session、delay 500 µs、各连续 10 分钟；代码版本 v4；完整报告见 [`docs/REPORT.md`](docs/REPORT.md)。

|---|---|---|---|---|---|---|---|
| A async-ping | 6514 万 | 0 | 0 | 180 ns | 330 ns | 429 ns | 120 / 270 ns |

  插值估计与置信区间是补充：p50 的 A − B +9.6 ns（95% 区间 +9.1 ~ +10.2），p99 −98.9 ns（−102.8 ~ −95.1）。
  **交替 10 对用来评估运行之间的波动和结论稳不稳**（它们不带样本导出）：p50 的 A − B +10.9 ns（+8.6 ~ +13.3，10 对全部为正），p99 −104.7 ns（−110.8 ~ −98.7，10 对全部为负）。
- **抽象税是正的，按"三段合计"算每个请求约 20 ~ 30 ns**：把三个被测段（① + ② + ③）的平均值加起来，主考核里 A 比 B 多 32.2 ns；
  交替 10 对是 +20.9 ns（95% 区间 +11 ~ +31，10 对全部为正）。它由三部分组成，§1.1 逐项说明。
  这是三段测量之和的差值，不是完整的 CPU 成本：T3 之后的收尾、主循环的空转不在任何一段里（§1.1）。
- **p99 的 A − B 为负不代表 runtime 更快**：有一段约 250 ns 的 CPU 停顿（等上一次发送最后那次写网卡寄存器的操作完成），
  在 B 那边落在计分的段①里，在 A 那边落在不计分的段③里。用三个实验定位了它（§4.3）；把它统一移到 T0 之前再比，
  **A − B 在每个分位数上都是正的：平均 +10.3 ns，p50 +10.4 ns，p99 +14.7 ns**，此时两边的段①相差不到 1 ns。
- **这段停顿躲不掉，但落在哪里可以安排**：A 的结构让它自然落在不计分的段③（两次发送之间隔着调度），所以按题目口径 A 的计分路径尾部比 B 短（p99 330 对 429），
  中位数高约 10 ns。这不是 runtime 独有的优势——B 在 T0 前加一条指令就能做到同样的事（p50 170、p99 320，不比 A 高）——也不稳固（见下一条）；
  但它给出一个可以带走的手法：必须付的等待，安排到非关键路径上去付（报告 §4.4）。
  工程上的取舍可以如实地说成一句话：**A 用计分路径上 p50 约 +10 ns、每请求总共约 20 ~ 30 ns 的代价，换来了可组合、易扩展的异步写法**。
- **v4 是一次外部代码审查之后的修正，同场配对没有检测到性能退化**（[`docs/REVIEW.md`](docs/REVIEW.md)，报告 §3.4）：六条意见全部属实、全部采纳，其中两条是行为缺陷——
  回复的身份（id、seq、回带的发送时间戳）现在在请求完成之前核对；A 的发送重试现在会响应停止。同场配对 6 轮，v4 相对 v3：A 的段② −1.1 ns（区间 −4.6 ~ +2.5），进程内 p50 −0.8 ns（−4.1 ~ +2.6）；B 同样如此。区间都跨过 0：在这个环境和样本量下没有检测到差别，不等于证明了零成本。
  **中间走过一次弯路**：第一版顺手删掉了 sleep 之后原有的那次核对，A、B 的慢发送占比都升高了几倍。用五个版本同场轮流的二分法查明，原因就是两次发送之间少了那一次函数调用——
  这也是上面那个机制最直接的一个证据。最终版保留了它。
- **这些数字有多可信**：时间戳分辨率是 10 ns（表里的差值用插值分位数给出，并限定了它的适用范围）；主考核导出了全部原始样本，用分块自助法给出 95% 置信区间；
  A / B 交替 10 对看运行之间的波动；比较两个版本只用同一次开机里轮流跑的配对数据。
  **在 v4 上没有重做的**：跨重启、跨日期的复测。v1 ~ v3 上做过（9 个会话、4 次开机、2 天）：p50 的差值与每请求总账在所有会话里符号一致，
  排名口径的 p99 差值不稳定（有一次连符号都翻了），见 `docs/HISTORY.md`。那些旧数字不能与上表直接相比——期间网络环境变过两次。
- **可靠性**：除 10 分钟主考核外，A、B 各连续跑了 30 分钟（A 2.05 亿、B 2.00 亿个请求，零丢包、零泄漏）；故障注入 25 个场景 × A / B 共 50 项全部干净收场；
  这一整套 67 次正常运行没有丢过一个包。
- kernel bypass 的收益（A 对系统 ping，实测速率对齐）：单路 p99 39 µs 对 47 µs、max 0.09 ms 对 0.41 ms；64 路 p50 115 µs 对 249 µs、p99 0.13 ms 对 0.58 ms，p99.99 0.23 ms 对 1.09 ms，max 0.47 ms 对 18.1 ms。

## 1. 核心问题：raw frame 从 `rx_burst` 进来，到 64 个 session 的 future 被唤醒，中间 runtime 提供了什么

```text
 NIC ──DMA──▶ RX 环 ──rx_burst──▶ reactor ──Driver::on_packet──▶ Mailbox::put ──wake──▶ 就绪队列
                        (T2)      rt 主循环      应用提供的分类器       rt 原语          rt executor
                                                                                          │
 session task ◀── future 返回 Ready ◀── executor 出队并 poll ◀────────────────────────────┘
    (T3)
```

1. **poll-mode reactor**（`rt::Runtime::run`）：主循环 busy-poll 调用 `rx_burst`，不睡眠、不用中断。
   对每个包调用应用提供的 `Driver::on_packet`（泛型参数，静态分发，可内联）。
2. **Driver（协议侧，应用提供）**：解析 Ethernet / IPv4 / ICMP，用 ICMP `id` 找到对应 session 的 `Flow`，
   检查 `seq` 是否是它正在等的那个，然后把 **mbuf 的所有权**连同 T2 一起放进它的 `Mailbox`。
3. **Mailbox**（`rt::sync`）：单槽信箱。`put` 存入值并调用登记在里面的 `Waker::wake`。
4. **Waker**（`rt::executor`）：data 里编码 `rt_id | 代数 | 任务号`，wake = 把任务号推进就绪队列（带去重位）。
   clone / drop 都是空操作：没有引用计数，也就没有原子操作。
5. **executor**：reactor 每分发**一个**包就立刻跑一遍就绪队列：出队 → poll 该 task →
   它的 future 从 `mailbox.recv().await` 返回 `Ready(reply)` → session 代码继续执行（T3）。

session 的代码就是 SPEC 要求的形状（`crates/async-ping/src/main.rs`）：

```rust
while !sh.stopping.get() {
    let stamp = send(&sh, id, seq).await;         // T0 → T1，段①（T0 = send() 的第一行）
    let reply = wait_reply(&sh, id, seq).await;   // T2 → T3，段②；超时也从这里返回 Err(Timeout)
    let t3 = rdtsc();                             // T3：本 task 从 wait_reply().await 恢复执行
    woke = sleep_until(t3 + sh.delay).await;      // 样本之外；期间 reply（及其 mbuf）被本 task 持有
    record(&sh, id, seq, stamp, reply, t3);       // 记录样本；reply 在这里 Drop → mbuf 归还
    seq = seq.wrapping_add(1);
}
```

（为突出形状省略了两行统计代码；与 SPEC §5 的区别只有：`send` 内部自己重试而不返回错误，
超时不用 `?` 退出循环——超时的请求计为丢失，session 照常继续。）

### 1.1 这条路径的成本：抽象税从哪里来、各占多少、还值不值得优化

A 比 B 多做的事，按"一个请求的一生"可以分到三处。下面每一处都说明：A 多做了什么（对着代码）、多花了多少（怎么量出来的）、还能不能省。

```text
timer 到期 ─[段③]─▶ T0 ─[段①]─▶ T1 ···等回复··· T2 ─[段②]─▶ T3 ─▶ 收尾（登记下一次 sleep）─▶ 回主循环
            ③发送侧调度                            ①接收路径本身        ②它让同一批里后面的包多等
```

**分解**（每个请求的平均值，A − B，ns。"mfence 口径"是把那段 CPU 停顿统一移到 T0 之前的 5 分钟运行；由报告 §5 的表生成）：

| 来源 | 落在哪一段 | **主考核** | **mfence 口径** | 在总账里占 |
|---|---|---|---|---|
| ① 接收路径本身 | 段② | **+8.9** | +7.7 | 约 30% |
| ② 同一批里排在后面的包多等 | 段② | **+1.8** | +1.8 | 约 6% |
| ③ 发送侧调度 | 段③（段①里不到 1 ns） | **+20.8** | +17.1 | 约 65% |
| **合计（每请求总账）** | | **+32.2** | **+26.6** | |

怎么量的：①是"批内第 1 个包"的段②差值（它没有排在任何包后面）；②是其余位置的包比第 1 个包多出来的差值，按各位置的占比加权；③是段① + 段③的差值。

**这个"合计"覆盖什么、不覆盖什么。** 它是三个被测段的平均值之和，不是完整的 CPU 成本：T3 之后的收尾（登记下一次 sleep、把状态存回 future、返回 executor）不在任何一段里，
只通过"让同一批里后面的包多等"间接体现在②里；主循环的空转也不在内；段③还包含排在别的 session 后面等的时间。所以它适合用来看"时间在三段之间怎么挪动"和作为排名口径的补充，不宜当成精确的 runtime 开销。
为了把它量全而在热路径上再加探针，会带来新的测量干扰，没有做。

**哪一项稳、哪一项不稳。** ②只由代码决定，换哪次运行都不动；①的波动约为时钟的半格；**③最不稳**——交替 10 对的每请求总账是 +20.9 ns（各对在 +1 ~ +48 之间），波动几乎全部来自③。
原因见下面"第 ④ 点"：③里有一部分不是指令的开销，而是那段停顿落在了哪里。v1 ~ v3 的跨重启复测里看到的也是同样的格局（`docs/HISTORY.md` 第 1 节）。

**① 接收路径本身（T2 → T3）。** B 在这里只做一次 `match` 就打 T3。A 多做的是 runtime 的全部接收机制（`crates/rt/src/sync.rs`、`executor.rs`）：

0. `Flow::accept`：核对回复的身份——`seq` 和回带的发送时间戳都要与在等的请求一致（v4 起；B 在同样的位置做同样的比较，所以它不产生 A − B）；
1. `Mailbox::put`：把 reply（mbuf 所有权 + T2 + 回带的时间戳）写进信箱，取出登记在里面的 Waker；
2. `Waker::wake`：经 vtable 的一次间接调用 → 通过线程局部变量找到当前 runtime → 核对 runtime 编号和任务槽的代数 → 任务号进就绪队列（置"已入队"标记）；
3. 回到 runtime 主循环，`run_ready` 出队、清标记、构造 `Context`；
4. 经 `Box<dyn Future>` 的 vtable 间接调用 `poll` → 状态机跳回 `recv().await` → 从信箱取出 reply → 返回 session → 打 T3。

用 `probe` 构建单独量过第 3 步和第 4 步：各自的 p50 是 20 ns，其中 18 ns 是探针自己多读的一次时钟，实际工作都只有几纳秒。
再往下分已经低于 10 ns 的时钟分辨率，没有测。

**② 同一批里排在后面的包多等。** `rx_burst` 一次取回多个包时，它们共用一个 T2，却只能逐个处理，后面的包要等前面的包处理完。
A 处理一个包的完整周期比 B 长（按批内位置拆开：A 每往后一个位置段②增加约 37 / 24 / 33 ns，B 是 25 / 14 / 14 ns），
多出来的十来纳秒是 T3 **之后**的收尾：session 恢复执行后要把收到数加一、创建 `Sleep`、通过线程局部变量找到 timer 表、分配槽位、入堆、把状态存回 future、逐层返回 executor。
B 在同样的位置只是改一个状态、往堆里放一个 deadline。约 14% 的包排在别的包后面，所以平摊到每个请求只有约 2 ns。

这一项在 v1 里是现在的两倍多（+5.5 ns）：按位置拆开之后发现 A 每往后一个位置比 B 多约 20 ns，带着这个数字去读收尾的代码，找到 `Sleep` 第一次被 poll 时多读了一次时钟（约 18 ns）。
v2 去掉了它，同场配对 36 轮全部下降（经过和数据见 `docs/HISTORY.md` 第 3 节）。

**③ 发送侧调度（timer 到期 → T0 → T1）。** B 在这里是"弹出到期的 session → record → 打 T0 → 发送"。A 多做的是（`crates/rt/src/timer.rs`、`executor.rs`）：
`Timers::fire` 把槽位标成已触发 → `Waker::wake`（间接调用 + 线程局部变量 + 入队）→ `run_ready` 出队 → 经 vtable `poll` → `Sleep::poll` 再查一次槽位、释放、返回 `SleepInfo` → 回到 session → `record` → 进入 `send()` 打 T0 → 通过 `with_port` 向 runtime 取端口 → 调用与 B 相同的发送函数。
落在段①里的只有最后的 `with_port`：mfence 口径下两边的段①平均相差不到 1 ns。其余都在段③，不计入排名指标。

**④ 有一部分不是 CPU 在干活，而是"更容易撞上那段停顿"。**（这一点是推断。）每次发送的最后一步——往网卡寄存器写门铃——要 250 ~ 300 ns 才完成，
期间后面的内存写入在 CPU 的写入队列里排队，队列满了 CPU 才停下来等（§4.3）。B 在这段时间里做的事少，常常还没填满队列门铃就写完了，等于白白躲过；
A 的调度要执行更多的内存写入，更容易把队列填满而停下来。这段停顿落在段③还是段②，取决于发送之后紧接着发生的是另一次发送还是一次收包，
所以①和③各自的数会此消彼长。报告 §3.4 的二分（两次发送之间少一次函数调用，慢发送就变多几倍）和 `docs/HISTORY.md` 第 1 节记录的"A 的尾部在某个时段变重、三段总和不变"都是同一类现象。

**还值不值得优化**

| 可以做什么 | 影响哪一项 | 收益 | 判断 |
|---|---|---|---|
| 登记 sleep 时不再多读一次时钟 | ② | 实测（同场配对 36 轮）：②从约 +6 降到约 +2.5，段② p99 的差值低约 12 ns | **已做**（v2，`docs/HISTORY.md` 第 3 节） |
| 把收尾里剩下的约 10 ns 再压一压（登记 timer 时省掉线程局部变量查找和一次借用检查） | ② | 最多再省 1 ~ 2 ns（②现在总共只有约 2 ns） | 不值得 |
| `RefCell` 换成 `Cell`；用泛型任务存储省掉一次虚调用；Waker 里直接带上队列地址，省掉线程局部变量 | ①、③ | 估计每项 1 ~ 2 ns，合计 3 ~ 5 ns（没有实测） | 不值得：低于时钟分辨率，测不准；而且线程局部变量那一步正是 Waker 内存安全的保证（§3），不能省 |
| timer 到期后直接 poll task，不经过就绪队列 | ③ | 估计几纳秒，且不计入排名 | 不值得 |
| 一批有多个包时，预取下一个包的数据 | A、B 共同的那次约 100 ns 的 cache miss | 两边的绝对值都会明显下降，A − B 不变 | 对真实系统最有价值；对本题的指标没有影响 |
| 发完之后主动把写入队列排空，把那段停顿固定安排在非关键路径上 | 尾部分位数的稳定性 | 现在停顿落在哪一段取决于两次发送之间恰好做了多少次写入（报告 §3.4）；主动安排可以让它不再随代码的细微改动而变 | 对真实系统有价值；按本题的口径，它等于改变 T0 之前的行为（两边都加就是 mfence 口径），所以没有做 |
| 弄清 A 的尾部为什么会在某些时段变重（`docs/HISTORY.md` 第 1 节） | 尾部分位数 | 它造成的波动（旧版本里 p99 的差值在 −120 与 +52 之间）比上面所有优化加起来都大 | **最值得投入的方向**；v4 上还没有做跨重启的复测 |

一句话：抽象税现在是每个请求约 20 ~ 30 ns，其中接收路径本身约 9 ns（一格），批内排队约 2 ns，发送侧调度约 17 ~ 21 ns（运行之间波动最大的一项）。
明显多余的那一步已经去掉；再往下就不是"少执行几条指令"的问题，而是 runtime 的写入模式与设备写入之间的相互作用。

## 3. 设计要点与亮点

- **unsafe 有明确的边界**：共 59 处，每处都有 `// SAFETY:` 说明（`scripts/check-compliance.sh` 会清点并核对）。
  - 47 处在 `dpdk`（其中 1 处在它的集成测试里）：对 DPDK 的 FFI 调用，以及 `rdtscp`、预取等指令。上层拿到的是下面这些安全的类型。
  - 6 处在 `rt`：自己实现 Waker 绕不开 unsafe（`RawWaker` 的 vtable 是 4 个 `unsafe fn`，但它们只把指针当整数用、从不解引用）；另有 2 处解引用"当前线程正在运行的 runtime"的线程局部指针。
  - 4 处在 `pingkit`（注册信号处理函数、绑核、读内核单调时钟、诊断开关里的 volatile 写），A、B 的 `main` 各 1 处（最后调用 `eal.cleanup()`）。
  - 协议解析（`pingproto`）、timer 堆（`timerq`）、session 逻辑、统计与报表不含 unsafe。
  - `Mbuf` 是唯一所有者，Drop 时归还 mempool；不实现 `Clone`；内含裸指针 → 自动 `!Send`。
  - `Mempool` 创建后泄漏为 `&'static`：从类型上保证 mbuf 不会比池活得久；创建时必须出示 `&Eal`（"EAL 已初始化"由签名保证）。
  - `Port` 刻意 `!Send + !Sync`：同一队列上的 rx/tx 不是线程安全的，交给编译器保证。同一个端口号只能领出一个句柄；`close` 会先停止。
    未启动 / 已停止时调用收发是无害的（DPDK 把收发函数换成返回 0 的空函数）——这几种顺序有实测（`crates/dpdk/tests/lifecycle.rs`，用 DPDK 自带的虚拟网卡）。
  - `RxBurst` 逐个交出所有权，没取走的在 Drop 时释放；`tx` 失败时把 mbuf 原样还给调用者。
- **Waker 的内存安全**：std 规定 `Waker: Send + Sync`，而本 runtime 是单线程的。
  wake 时通过线程局部变量确认"当前线程正在运行的就是这个 runtime"（比对 rt_id），否则 abort——
  绝不会在别的线程上碰非线程安全的就绪队列。任务槽带代数，过期 waker 唤醒不到复用了同一槽位的新任务。
- **固定容量、零热路径分配**：任务槽、就绪队列在创建时分配好，永不扩容；timer 槽位复用；
  每包只做一次 mempool 取 mbuf（cache 命中）。
- **timer 精确到 TSC**：二叉堆（64 个 timer，O(log n) 且无槽粒度误差）；`sleep` 返回
  `SleepInfo { deadline, fired_at }`，用于统计 sleep 误差与段③；取消是 O(1)（标记后在弹出时回收）。
- **ICMP 校验和**：对"id / seq / TSC 为 0"的模板预先算好反码部分和，每包只加 6 个 16 位字
  （RFC 1624 的思路）。由于反码加法满足交换律，结果与全量重算**逐位相同**，单测用 100 万组随机数据交叉验证。
- **ARP 应答**：原地改写收到的 request 再发回（实测对端确实会通过 ARP 问我们的 MAC）。
- **ENA 专项**：igb_uio + `wc_activate=1` 打开写合并（LLQ 依赖它；用 PAT 表确认了 BAR2 为 write-combining）；
  主循环周期性调用 `rte_timer_manage()`（ENA watchdog 依赖应用驱动 rte_timer）；注册 reset 事件回调；
  空闲时主动 `tx_done_cleanup`，尽量不让 TX 回收落进段①。
- **测量方法本身经过验证**（详见 §4）：发现并修正了 rdtsc 乱序执行造成的系统性偏差、启动阶段对 sleep 误差的污染；
  标定出时间戳的分辨率只有 10 ns 并用插值分位数应对；给 A − B 配了置信区间和多轮交替对比；
  主循环自带"被外部打断"的检测，最大值尖刺可以直接归因。
- **收到的包先验明正身**：echo reply 必须来自对端 IP，并且 `id`、`seq`、回带的发送时间戳三者都与在等的请求一致，才会交给 session；record 时再用 session 自己记下的 T0 核对一次。

### 相位设计（64 个 session 的相位关系）

- **初始相位**：64 个 session 均匀错开在一个 delay 周期内（相邻 7.8 µs），不让它们同时发、同时回。
- **稳态相位不由我们决定**：这是闭环（收到 reply 再 sleep 再发），每个 session 的周期 = RTT + delay。
  对端网卡的中断合并会把相近时刻到达的请求攒成一批处理、一批回复，于是这些 session 的 T3 相近、sleep 同时到期、下一次发送也挤在一起。
  实测两边都有约 80% 的发送距上一次发送不到 2 µs；非空 rx_burst 里 1 个包占 77%、2 个占 18%、3 个占 4%、4 个占 0.6%。
- **没有做的事**：给 delay 加随机抖动来打散相位。它会改变 `--delay-us N` 的语义，而且对端仍会重新把它们捏成批次。
- **为什么要在意**：批次越大，同一批里靠后的包等得越久（段②的 p99，报告 §5 按批内位置做了拆分），连续发送也越多（段①的停顿，见 §4.3）。
  runtime 的应对是"每分发一个包就立刻 poll 它的 task"，让靠前的包不被整批拖慢。

### 取舍：时间花在哪、没花在哪

| 投入了 | 理由 |
|---|---|
| A 与 B 共用除调度之外的全部代码 | 否则 A − B 不是抽象层成本 |
| 验证测量工具本身（rdtsc → rdtscp、起点延后、停顿检测） | 这三处任何一处不处理，报出来的数字都是错的 |
| 把每个异常数字追到原因（段①尾巴 → CPU 写入队列被设备写入堵住；sleep 误差 max → 启动假象；外来回复 → 源 IP 检查） | SPEC 问的是"你是否知道它收在哪里" |
| 给数字配不确定度（原始样本、分块自助、交替 10 对）；主动做故障注入 | 一个没有区间的差值没法判断是不是噪声；"没出事"不等于"出了事也能收场" |
| 对账与零泄漏的可核对性（发送对账、收包对账、mbuf 记账） | 硬门槛，且要能"自洽解释" |

| 没有投入 | 理由 |
|---|---|
| 进一步压榨段②（RefCell → Cell、泛型任务存储省 vtable、缩短 T3 之后的收尾） | 接收侧的税在 p50 上只有一格（约 10 ns），接近测量分辨率；各项的来源、占比和一项已实测的优化见 §1.1 |
| 每个 session 一个预构建模板 mbuf + refcnt（省掉分配和 106 B 拷贝） | A、B 同样受益，不改变 A − B；且要处理"网卡还在读时不能改模板" |
| 攒批发送、或人为拉开 B 的发送间隔 | 前者改变 T1 的语义，后者是故意拖慢 B，都会让 A − B 失真 |
| 时间轮、每包一个超时 timer | 只有 64 个 timer；超时用 100 µs 一次的扫描即可，没有每包的堆操作 |

## 4. 测量方法

### 4.1 四个时刻（A 与 B 语义相同、调用同一个打点函数）

| | A | B |
|---|---|---|
| **T0** | `send()` 的第一行（早于向 runtime 查找端口） | 循环里 `record(上一个 reply)` 之后、调用发送函数之前 |
| **T1** | `tx_burst` 返回（同一函数内） | 同左 |
| **T2** | `rx_burst` 返回（runtime 主循环） | `rx_burst` 返回（B 的循环）；同一批包共用一个 T2 |
| **T3** | task 从 `mailbox.recv().await` 恢复后的第一行 | 状态机拿到 reply、可以开始算延迟的那一刻 |

- **进程内耗时 = (T1 − T0) + (T3 − T2)**（排名指标）；端到端 = T3 − T0。
- **sleep 误差** = timer 发现到期的时刻 − deadline；**段③** = 发现到期 → 下一个 T0。
  SPEC 的"段③ = sleep 到期 → 下一个 T0"里，"到期"也可以理解成 deadline 本身，所以另报一行 **deadline → 下一个 T0**（= sleep 误差 + 段③），两种读法都覆盖。
- 按 SPEC 的 loop 形状，样本在 sleep **之后**的 `record(reply)` 处记录，reply 的 mbuf 在 sleep 期间一直被持有。
- **B 的 T0 为什么不取在"timer 判定到期"的那一刻**：A 的顺序是 sleep 返回 → `record(reply)` → `send()` 入口（T0），
  record 不在 A 的段①里。B 若把 T0 提前到判定到期的那一刻，它的段①就会多包含 record 的开销，两边不再对齐。
  所以两边的 T0 都紧挨在"发送这件事"之前，record 都落在段③里。
- **运行起点定在启动后 1 ms**：创建 runtime、分配直方图、spawn 任务要花约 100 µs。早期版本把起点取在这些准备工作之前，
  前几个 session 的初始 deadline 在主循环开始转之前就已过期，被记成"sleep 迟到 80–190 µs"，污染了 sleep 误差的最大值。

### 4.2 为什么用 `rdtscp` 而不是 `rdtsc`（关键发现）

最初用 `rdtsc` 打点，A − B 的段② p50 是 **+120 ns**。把段②拆开后发现：executor 的出队 + poll 只有约 20 ns，
大头在"分类"这一步——读网卡刚 DMA 进来的包数据，是一次 cache miss（约 100 ns）。
B 从分类到 T3 只隔几条指令，而 **rdtsc 不是序列化指令**：乱序执行可以在 miss 结束前就把 rdtsc 执行掉，
这 100 ns 就从 B 的段②里"消失"了；A 从分类到 T3 之间有几百条指令，乱序窗口塞不下，只能等 miss 结束。
改用 `rdtscp`（等前面所有指令完成、所有读都落地才读 TSC）后，B 的段② p50 从 10 ns 变成 120 ns，
**A − B 的段② p50 从 120 ns 变成约 10 ns**。所以正式版的所有打点都用 `rdtscp`（每次约 18 ns，两边相同；程序启动时会标定并写进报告）。

### 4.3 段①的尾巴不来自 runtime：三个实验

两边的段①执行的是同一个函数，尾巴却不同。用 `probe` 构建把段①拆成三步后（A、B 相同）：
"取 mbuf"和"写包"直到 p99.99 都是平的，**尾巴全部在 `tx_burst` 里**。它有两个来源：

1. **紧跟在上一次发送之后的发送**。对端的中断合并让 reply 成批到达，多个 session 的 sleep 同时到期、发送扎堆。
   B 有约 2.4% 的发送距上一次发送不到 100 ns，这些发送的段①约 310 ns（正常是 50 ns）；A 相邻两次发送的间隔几乎从不低于 250 ns，没有这样的发送。
   这就是 p99 的 A − B 为负的全部来源。用诊断开关 `--diag-pre-t0`（在读 T0 **之前**多做一件事）做了三个实验来定位它：

   | 读 T0 之前多做的事 | 结果 |
   |---|---|
   | 一条 `sfence` | **没有任何变化**（否定了最初的猜测"卡在驱动的 sfence 上"） |
   | 一条 `mfence`（等此前所有写入真正完成） | B 的慢发送消失，停顿移到段③；A − B 在每个分位数上都变成正的 |
   | N 次普通的内存写入，不带任何栅栏指令 | N ≤ 36：没有变化；N = 40：大部分消失；N ≥ 44：效果与 `mfence` 相同 |
   | （反方向，报告 §3.4）两次发送之间**少**做一次函数调用 | A、B 的慢发送都变多几倍；加回来就恢复 |

   三个实验指向同一个机制：发送的最后一步是往网卡寄存器写"门铃"，这次写入约 250 ~ 300 ns 才真正完成；CPU 不等它，
   后面的写入在 CPU 的写入队列（store queue）里排队，门铃没写完它们都出不去；**队列被填满时，CPU 才停下来等**。
   B 两次发送之间做的事少、写入少，队列在下一次发送的中途填满（落在段①）；A 多了调度，写入更多，在走到 T0 之前就填满了（落在段③）。

   示意（1 个字符 = 10 ns；pkt1 / pkt2 是连续要发的两个包）：

   ```text
   ns          0    50   100  150  200  250  300  350  400
               |----|----|----|----|----|----|----|----|
   doorbell        [== pkt1's doorbell write in flight ==]

   B  pkt1     [###][..]
   B  pkt2             [#~~~~~~~~ stalled ~~~~~~~~~~~][##]
                       ^T0                               ^T1
                       |<-------- seg1 = 300 ns -------->|   <- ranked

   A  pkt1     [###]
   A  sched        [..... scheduling ....~~ stalled ~]       <- seg3, NOT ranked
   A  pkt2                                           [###]
                                                     ^T0 ^T1
                                                     |<->|   <- seg1 = 50 ns, ranked

   [###] tx_burst    [...] our own code    [~~~] CPU stalled: store queue full behind the doorbell write
   ```

   两边的第二个包都在约 400 ns 时交给网卡，A 并没有更快；这段停顿在 B 那边算进段①（计分），在 A 那边算进段③（不计分）。
   按平均值算总账，A 每个请求比 B 多约 20 ~ 30 ns；把停顿统一移到 T0 之前（两边都加 `mfence`）再比，A − B 是 p50 +10 ns、p99 +15 ns，每个分位数都为正（报告 §4）。
   需要如实说明：这台虚拟机没有开放硬件性能计数器，"写入队列被堵住"是与三个实验都吻合的解释，不是直接观测到的。
2. **发送队列的位置**。即使间隔足够，仍有一小部分 `tx_burst` 要 150 ~ 270 ns。按"发送计数 % 32"统计，
   慢的占比以 4 个条目（512 B 设备内存）为周期起伏。A 和 B 都有这个规律——这是网卡 / PCIe 一侧的行为，软件控制不了。

**对读数的影响**：第 2 类慢发送的占比在不同的运行之间会变（A：这次交替的 10 轮里是 0.22% ~ 0.50%，主考核是 0.87%）。段①的分布是两段式的，
所以它的 p99 落在哪一段只看这个占比在 1% 的哪一边：低于 1% 读数是 70 ~ 80 ns，高于 1% 就跳到 130 ns 以上。
程序因此把这个占比直接报出来（"段① ≥ 125 ns 的样本占 x%"），它比 p99 本身更稳定、更有解释力。

### 4.4 这些数字有多可信：分辨率、置信区间、交替多轮

- **时间戳分辨率是 10 ns。** 程序启动时会标定时钟：这台机器的 TSC 读数每 10 ns 才跳一步（一步 26 个周期），所以任何时间差都是 10 ns 的整数倍，
  两个分位数相减也只能得到 10 ns 的整数倍。单个样本有 ±10 ns 的量化误差，但平均值没有偏差。
  为了看清一格以内的差别，程序另外给出**插值分位数**（把同一格的样本看成均匀分布在格内，再线性插值；JSON 里的 `p50_interp` 等），
  单元测试用模拟的量化时钟验证了它。**适用范围**：只对 1.6 µs 以内的值成立（那里直方图的桶宽不超过一格）——进程内耗时、段①、段②都在这个范围里；
  更大的值（端到端延迟）只在桶内插值，报告里一律用普通分位数。插值是模型估计，小数位数不代表测量精度。
- **置信区间。** 运行时加 `--samples` 会把全部原始样本导出；`scripts/ci.py` 用分块自助法算 95% 区间：先分别求 A、B 的分位数再相减；
  以 20 秒的时间块为单位重抽（样本并不独立，把 1 亿个样本当成独立的，区间会窄几十倍）。
- **交替多轮。** 对端的状态每次运行都不同（往返时间会在两档之间切换），会改变 reply 的到达批次，从而影响尾部。
  这部分波动单次运行的区间看不到，所以用 `scripts/ab.sh` 让 A、B 交替各跑 10 轮，对逐对的差值做统计，并核对先后顺序没有影响。
  正式成绩仍是 600 秒主考核；这 10 对回答的是"换一次运行，结论还在不在"，而且它们不带样本导出。
- **比较两个版本只用同场配对。** `scripts/versions-ab.sh` 让旧版本和当前版本的 A、B 四者在同一次开机里轮流跑，逐轮配对。
  拿两组不同时段的数字直接相减，会把时段之间的波动算成代码的差别——这个错误犯过一次（`docs/HISTORY.md` 第 3 节）。
  v4 的修改就是这样验证的；第一版改差了，也是这样发现、再用五个版本同场轮流的二分法定位的（报告 §3.4）。
- **测量工具本身也要验证，而且不能只看平均值。** 样本导出"按设计"不在被测段里，平均值上也看不出影响，但它改变过段①的尾部（v3 已修正，`docs/HISTORY.md` 第 2 节）。
  系统 ping 的速率也不能按参数推算，要实测（§4.5）。
- **换一次开机、换一天。** 这一项在 v1 ~ v3 上做过（9 个会话、4 次开机、2 天；`scripts/session.sh`、`scripts/day.sh`）：p50 的差值和每请求总账的符号稳定；
  尾部分位数的差值会随时段大幅变化，连符号都会变；会话之间的波动比单次运行的置信区间大几倍；绝对值会成段地漂，A − B 不跟着漂（`docs/HISTORY.md` 第 1 节）。
  **v4 上还没有重做**，本文的全部数字来自同一次开机里的连续几个小时。

### 4.5 C 为什么能和 A 相减

- **同一路径**：同一对端、同一子网，只是本端换成内核网卡（device-number 0）；
- **同样的帧**：`ping -s 64` → 106 B，与 A 相同；
- **同样的并发，速率实测并对齐**：64 个 ping 进程 = 64 路（ICMP id 各不相同），每路 1 ms 间隔
  （iputils 的 `-i` 以整数毫秒计，实测 `-i 0.0005` 会退化为"收到即发"）。**名义上是 6.4 万包/秒，实测是约 6.2 万**：
  每个 ping 结束时会报告自己实际跑了多久（名义 60 秒的要 61 ~ 62 秒），`scripts/summarize_c.py` 用它算实际速率。
  然后给 A / B 选 delay，使它们的实测速率与 C 对齐（先试跑 10 秒量一次、再修正一次；这次是 `--delay-us 940`，A 61,601、C 62,059 包/秒，相差 0.7%）；
- **同样的口径**：默认用 `ping -U`（用户态到用户态），对应 A 的 T3 − T0。ping 默认的口径是"用户态发送 → 内核收包时间戳"，
  不含唤醒进程与拷贝到用户态，会低估内核路径的开销；两种口径都给出；
- **为什么速率必须对齐**：实测对端 RTT 随速率非单调变化（最初的环境下：1 路 62 µs、8 路 160 µs、32 路 107 µs、64 路 245 µs），
  是对端网卡驱动的自适应中断合并。速率不同，对端状态就不同，相减就没有意义。
- **没有对齐的是负载的形状**：A 是闭环的（收到回复后等 delay 再发），ping 是开环的（按固定间隔发，不管回复到没到）。
  即使平均速率对齐，相位、批量和在途请求数的分布也不同，所以 A 与 C 的差值是"这个环境、这种负载下"的读数，不能全部归因于"有没有绕过内核"。

## 5. 超时、丢包与异常处理

- **超时**：默认 `--timeout-us 10000`（10 ms，约为正常 RTT 的 40–150 倍）。超时由维护节拍（每 100 µs）扫描，
  实际生效的超时落在 [10 ms, 10.1 ms]。**超时的请求计为丢失（timeouts）**，不进入延迟分布；session 照常 delay 后发下一个 seq。
- **迟到**：超时之后才到的 reply，用每个 session 最近 4 个超时 seq 识别，计为 `late`，释放 mbuf，
  绝不会被当成新 seq 的回复。其他对不上的 echo reply 计为 `unexpected`。
- **外来回复**：echo reply 必须"目的 IP 是我、源 IP 是对端"才会进入分发逻辑。实测遇到过别的主机发来的 echo reply（id=16509）；
  这类包计为 `foreign` 并记下源 IP，**绝不交给 session**（否则只要 id / seq 碰巧合法，就会产生一个错误的延迟样本）。
- **回复的身份在请求完成之前核对**（v4）：`id`、`seq` 和回复带回的发送时间戳三者都与在等的那个请求一致，才算收到。
  `seq` 只有 16 位，每个 session 约 43 秒回绕一次，迟到很久或被重放的旧回复有可能撞上当前的 `id/seq`；时间戳每个请求都不同。
  对不上的回复被拒绝，计为 `tsc-mismatch`，**在途的请求和它的超时时刻原样保留**：之后真正的回复照常完成它，一直不来则照常超时。
  判定由 A、B 共用的 `pingkit::matching::judge` 给出，发生在 T2 → T3 之内。sleep 之后 `record` 时再用 session 自己记下的 T0 核对一次（`record-mismatch`，应恒为 0）。
- **收包对账**：收到的每个包必须恰好落入一类，报告打印 `rx − (received + late + unexpected + foreign + tsc-mismatch + other + arp)`，必须为 0。
- **最大值尖刺的归因**：主循环自带停顿检测——一轮什么都没干的空轮询超过 1 µs、或收到包那一轮在取包之前超过 10 µs，
  就记为一次"被外部打断"。A 和 B 的次数几乎相同（约每秒 200 次、累计占 0.06%），sleep 误差与进程内耗时的最大值都能对上其中最长的一次，
  说明这些尖刺来自虚拟机宿主机而不是程序本身。
- **对账**：报告里打印 `sent − received − timeouts − in-flight-at-end`，必须为 0；丢包 = timeouts，其中多少最终迟到收到也一并给出。
  用 `--timeout-us 150`（比 RTT 还短）做过压力验证：两边都是 timeouts = late、对账为 0、零泄漏。
- **AWS 静默丢包的证据**：报告给出 ENA 的 `bw/pps/conntrack/linklocal_allowance_exceeded` 在本次运行中的增量。
- **零 mbuf 泄漏核对**：mempool 刚创建（端口未启动）时记下 avail 作为初值；结束时先 drop 所有 task / 信箱 / 持有的 reply，
  再 `tx_done_cleanup` + `stop` 端口（PMD 归还 RX / TX 环上的 mbuf），然后比较 avail。泄漏非 0 时进程退出码为 3。
- **网卡 reset**：注册了 `RTE_ETH_EVENT_INTR_RESET` 回调；ENA watchdog（保活超时、TX 完成丢失）触发时，
  程序停止并照常输出统计、核对 mbuf，退出原因写在报告里。
- **SIGINT / SIGTERM**：不依赖它们停止；收到时走与到时相同的收尾流程（停止发送 → 等在途请求 → 统计 → 核对）。
- **TX 环满 / mempool 取不到 mbuf**：计数后 1 µs 再重试（A 与 B 相同），不丢弃 session；进入停止阶段后不再重试、不再发新请求，所以发送持续失败也不会让程序退不出去（v4 修正，有 5 个专门的故障场景）。
- **同一张网卡只允许一个进程驱动**：igb_uio 不阻止第二个进程打开同一个设备，两个进程同时驱动会互相破坏收发队列。
  程序启动时先拿一把文件锁（`/run/bqping-<PCI>.lock`），拿不到就报错退出；锁随进程结束自动释放，崩溃后也不需要手工清理。
- **以上每一条都有对应的故障注入场景**（`scripts/fault.py`，报告 §8）：每个场景都核对没有崩溃、零泄漏、两条对账为 0。

### 5.1 遇到的异常（汇总）

做这个项目过程中真正碰到的、比较重要的异常。状态分三种：**已解决**（原因清楚，已处理）、**已解释**（原因清楚或有实验支持，但不是能"修掉"的东西）、**未定位**（说明卡在哪里）。

| # | 现象 | 原因 / 解释 | 状态 |
|---|---|---|---|
| 1 | 段② 的 A − B 最初测出来是 +120 ns | 用 `rdtsc` 打点：它不等前面的指令执行完，B 读包数据的那次 cache miss 被"藏掉"了。改用 `rdtscp` 后约 +10 ns（§4.2） | 已解决 |
| 2 | sleep 误差的最大值有几十微秒 | 运行起点取在准备工作之前，头几个 session 的第一次 sleep 被记成"迟到"。起点改到启动后 1 ms（§4.1） | 已解决 |
| 3 | 别的主机发来的 echo reply 被当成"对不上号的回复" | 公网上某台机器约每 14 分钟往这张网卡的公网 IP 发一个 echo reply。加了源 IP 检查，只认对端（§5） | 已解决 |
| 4 | A 处理一个包的周期比 B 长约 20 ns，同一批里后面的包多等 | 登记 sleep 时多读了一次时钟。去掉后（v2）同场配对，三次开机共 36 轮全部下降（`docs/HISTORY.md` 第 3 节） | 已解决 |
| 5 | **p99 的 A − B 是负的**（A 看起来比 B 快） | 上一次发送的门铃写入约 250 ns 才完成，CPU 的写入队列被它堵住；这段停顿在 B 落在段①、在 A 落在段③。三个实验加一次二分支持（§4.3、报告 §3.4）。机制本身是推断：虚拟机里没有硬件计数器可以直接看到队列 | 已解释 |
| 6 | 所有时间差都是 10 ns 的整数倍 | 这台机器的 TSC 读数每 10 ns 才跳一步。报告分辨率，并用插值分位数看一格以内的差别（§4.4） | 已解释 |
| 7 | 最大值有几十到一百多微秒的尖刺 | 虚拟机宿主机偶尔夺走 CPU：主循环的停顿检测显示每秒约 200 次，A、B 相同，最大值能对上最长的一次停顿。隔离不掉 | 已解释 |
| 8 | 往返时间随速率非单调变化，同一次运行里也会在两档之间切换 | 对端网卡驱动的自适应中断合并（从本机一侧的表现推断；对端不可见）。所以排名只看进程内耗时，A 与 C 必须把速率对齐再比 | 已解释 |
| 9 | 两天里各有一次：一次运行里突然 64 个超时（每个 session 一个）+ 上千个重复的回复，主循环停顿约 30 ms；此后往返时间明显变短（下限 52 → 36 → 24.5 µs，64 路的中位数 160 → 53 µs） | 判断是实例或网络路径被云平台切换了。程序两次都没崩、零泄漏、对账为 0、无错配（`docs/HISTORY.md` 第 4 节）。**无法确认**：看不到云平台一侧的日志。第二次打断了一次正在进行的整套测量，那一次作废重测 | 已解释（推断） |
| 10 | 满 MTU、单向 1.2 Gbit/s 时有百万分之几十到一百多的丢包 | A、B 相同；本机网卡和 AWS 限额计数全为 0；换小包或降速就消失 → 不是在本机丢的。**丢在链路还是对端无法定位**：对端的计数器读不到 | 已解释到"不在本机" |
| 11 | 偶发的单个丢包：v1 ~ v3 的四十多亿个请求里出现过 4 次"一次运行恰好丢 1 个"（B 3 次、A 1 次） | 网卡的发送计数表明请求确实发出去了，接收侧没有任何丢弃计数，当时最长停顿远小于超时 → 不是在本机丢的。**无法进一步定位**：对端不可见。有一条没证实的线索（`docs/HISTORY.md` 第 5 节）。v4 的这一套数据里没有出现 | 未定位 |
| 12 | **A 的尾部在某个时段变重**：v1 重启后约 20 分钟，段①、段②的尾部变长、段③变短（三段总和不变），p99 的 A − B 从 −107 变成 +52；B 不受影响 | 已排除：代码差异、样本导出、本机其他核、网卡整体变慢、宿主机打断。之后又重启两次、300 次 A 的运行，v1、v2 都没有再出现。**触发条件未查明**：无法按需复现；没有硬件计数器。它与第 5 项是同一类现象（时间在三段之间挪动），所以总账和 p50 的差值不受影响（`docs/HISTORY.md` 第 1 节）。v4 上没有做跨重启的复测 | 未定位 |
| 13 | 即使发送间隔足够，仍有零点几个百分点的 `tx_burst` 要 150 ~ 270 ns，占比以发送队列每 4 个条目为周期起伏 | A、B 规律相同 → 在网卡 / PCIe 一侧，与 runtime 无关（报告 §7）。**具体原因未查明**：设备内部不可见 | 未定位 |
| 14 | 绝对值在一次开机之内会成段地漂（v2 时见过：三个程序的段② p99 同时升高 15 ~ 20 ns，一小时后回落又升高） | 三者同步、往返时间没变 → 不是 runtime 的问题，是环境。A − B 在整个过程中不变，所以所有结论都用"交替 / 轮流跑再配对"得出（`docs/HISTORY.md` 第 1 节） | 已解释到"与 runtime 无关" |
| 15 | 开了样本导出（`--samples`），A 的慢发送占比从约 0.5% 升到 3% ~ 4.6% | 每 8 个样本要写一条不在缓存里的缓存行，这次写入挂在 CPU 的写入队列里，拖慢紧随其后的发送——与第 5 项同一个机制。写样本时预取下一条缓存行后消失（v3，`docs/HISTORY.md` 第 2 节）。B 带样本导出时慢发送总落在较低的一档，这一点没有查明，所以最终的 A − B 以不带样本导出的交替数据为准 | 已解决（B 的那一点未定位） |
| 16 | **v4 的第一版让 A、B 的慢发送都变多了几倍**（A 约 0.3% → 2% ~ 10%，B 约 3% → 11% ~ 20%），进程内 p99 各高几十纳秒 | 第一版顺手删掉了 sleep 之后原有的那次核对；它位于两次发送之间，少了这次函数调用，那段停顿就更多地落进段①（第 5 项的机制）。同场对比发现、五个版本的二分定位、保留那次核对后恢复（报告 §3.4） | 已解决 |
| 17 | 外部代码审查指出的两处行为缺陷：`id/seq` 一对上请求就算完成，回带的时间戳事后才核对；发送持续失败时 A 到时间也退不出去 | 都属实。前者没有实际发生过（全部运行里时间戳不符的计数都是 0），后者在修复前复现了。v4 已修正并有测试（`docs/REVIEW.md` R1、R2） | 已解决 |
| 18 | 故障注入的 `mbuf-exhaust` 场景里，丢得多的时候有约 2% ~ 17% 的丢失不在网卡的 `imissed` 里 | 用实验版程序打印了全部变化的网卡计数器：不在任何别的计数器里，请求都发出去了，也不是计数器滞后。**这部分未被现有计数器解释，具体丢在哪里没有确定**。只在这个故意配坏的场景里出现；正常配置下的正式运行没有超时（报告 §8） | 未定位 |

未定位的四项（11、12、13、18）有一个共同点：都发生在我们看不到的地方（对端、云平台、网卡内部），或者无法按需重现。它们对结论的影响已经量化——
第 11 项是约十亿分之一的丢包；第 12、13 项只影响尾部分位数的差值，不影响每请求总账和 p50 的差值；第 18 项只出现在故意配坏的场景里。

## 6. 怎么跑

### 6.1 在考察机上：已经部署好，登录就能跑

考察机上环境、代码、可执行文件都是现成的，不需要安装或编译任何东西：

| 已经就绪的 | 在哪 / 是什么 |
|---|---|
| 仓库与可执行文件 | `~/dpdk-async-ping`，`target/release/async-ping`（A）、`raw-ping`（B）已编译（release） |
| 工具链 | Rust 在 `~/.cargo`，DPDK 25.11.3 在 `/usr/local`，`igb_uio` 模块已编译 |
| 内核启动参数 | 核 3 隔离、1024 × 2 MiB 大页，已写入引导项，**重启后仍然有效** |
| 网卡配置 | `config/nic.env`（PCI 地址、本机与对端的 IP / MAC，自动探测生成）；只有 device-number 1 的那张会交给 DPDK，SSH 所在的网卡不动 |

重启之后唯一会丢的是"网卡绑定到 DPDK"这一步，`run.sh` 每次运行都会自动补上，所以**重启后也不需要任何手工操作**。

**现场的 60 秒**（SSH 登录后）：

```bash
cd ~/dpdk-async-ping
scripts/check-env.sh                                   # 可选，不到 1 秒，只读：隔离核、大页、驱动、网卡逐项打 ✔
scripts/run.sh A --delay-us 500 --duration-sec 60      # A：跑在自研 runtime 上
scripts/run.sh B --delay-us 500 --duration-sec 60      # B：手写 busy-poll，对照
```

每次运行约 65 ~ 70 秒（60 秒测量 + 启动与收尾），结束时打印一份报告。看这几行就够了：

```text
sent 6910949  received 6910949  timeouts 0  late 0  in-flight-at-end 0  unexpected 0  foreign 0  tsc-mismatch 0  ...
对账：sent − received − timeouts − in-flight = 0（应为 0）；丢包 = timeouts = 0（其中 0 个迟到收到）
收包对账：rx 6910950 − (received + late + unexpected + foreign + tsc-mismatch + other + arp) = 0（应为 0）

metric (ns)                       count      min     mean      p50      p90      p99    p99.9   p99.99        max
in-process ①+②  [排名指标]          6910949       60      186      180      220      320      401      521      16820
seg① send  T1−T0                6910949       40       54       50       60       70      160      250       5710
seg② recv  T3−T2                6910949       20      132      120      170      270      340      450      16760
...
mbuf：pool 8191，初值 avail 8191（端口启动后 7168），关停后 avail 8191 → 泄漏 0 ✔
退出原因：到达 --duration-sec，停止发送并等在途请求收尾
构建：commit e50c0f882898 · rustc 1.98.1 (48a229cea 2026-09-01) · DPDK 25.11.3 · release
```

（上面是 2026-10-02 在考察机上用 v4 按这条命令原样跑出来的 A。紧接着跑的 B：`in-process` 一行是 p50 170 / p99 429，同样零丢包、零泄漏。）

- **零丢包**：`timeouts 0`，对账那一行等于 0；
- **零泄漏**：最后的 `泄漏 0 ✔`（mbuf 池关停后的可用数回到初值）；
- **排名指标**：`in-process ①+②` 一行；A 与 B 的同一行相减就是 A − B（p50 约 +10，p99 约 −100；为什么 p99 是负的见 §4.3）；
- 运行过程中每 5 秒打印一行进度（已发、已收、超时数、每秒请求数）。

**接着可以跑的**（都在仓库根目录）：

```bash
scripts/run.sh A --delay-us 500 --duration-sec 600     # 10 分钟主考核（B 同理）
scripts/run.sh C --duration-sec 60                     # C：系统 ping（走内核网卡，不占 DPDK 网卡）
scripts/ab.sh 3 60                                     # A/B 交替 3 对，每轮 60 秒，结束时打印逐对差值（约 7 分钟）
scripts/fault.py                                       # 故障注入矩阵：25 个场景 × A/B（约 5 分钟）
scripts/check-compliance.sh                            # 逐条核对 SPEC 的硬性要求（32 项，约 20 秒，含编译检查与单元测试）
source ~/.cargo/env && cargo test --release --workspace   # 只跑测试（50 个，不需要网卡）
```

**几点提醒**

- **一次只能跑一个 A 或 B**：它们独占同一张网卡。第二个实例会在几秒内退出，并提示"网卡 … 正被另一个 async-ping / raw-ping 进程使用……已拒绝启动"（锁文件 `/run/bqping-<pci>.lock`），不会干扰正在跑的那个。
- **随时可以 Ctrl-C**：程序会停止发送、等在途请求收尾、照常打印报告并核对 mbuf 泄漏。
- **输出在哪**：屏幕上的内容同时写入 `logs/<A|B>-<时间>.log`，同名 `.json` 是机器可读的报告；已有的测量数据（当前版本最新的一套）在 `logs/` 下各子目录，汇总在 `docs/REPORT.md`；随手运行产生的这些文件不进仓库。
- **长时间测量期间不要在这台机器上编译**（会污染尾延迟，见 §7）。`run.sh` 自带的增量编译在代码没改时是空操作。
- `sudo` 免密；DPDK 在没有 IOMMU 的机器上需要 root 读物理地址，`run.sh` 已处理。

### 6.2 在一台新机器上从零开始

```bash
git clone <repo> ~/dpdk-async-ping && cd ~/dpdk-async-ping
scripts/setup.sh              # 一键环境：工具链、Rust、DPDK、igb_uio、大页、核隔离、中断
sudo reboot                   # 仅第一次：核隔离与大页的启动参数需要重启生效
scripts/check-env.sh          # 重启后自检（只读）
scripts/run.sh A --delay-us 500 --duration-sec 60      # 之后与 §6.1 相同
scripts/campaign.sh                                    # 一键重测报告里的全部数据并重新生成报告（约 2 小时）
```

`setup.sh` 是幂等的、分阶段的（`scripts/setup.sh <阶段>` 可单独重跑某一步）；网卡参数由 `scripts/detect-nic.sh` 自动探测并写入 `config/nic.env`，换网卡见 §8。

### 6.3 参数与直接运行

- 也可以不经过脚本，在仓库根目录直接运行可执行文件（网卡参数自动从 `config/nic.env` 读取；网卡需已 `scripts/bind.sh`）：
  `sudo target/release/async-ping --delay-us 500 --duration-sec 60`
- `run.sh` 会自动：重新绑定网卡（重启后网卡会回到内核）、增量编译、以 root 运行（无 IOMMU 时 DPDK 需要读物理地址）、
  把输出写入 `logs/<A|B>-<时间>.log`，报告写入同名 `.json`。
- A / B 的参数：`--delay-us`、`--duration-sec`（必填），`--sessions`（默认 64）、`--payload`（默认 64）、
  `--timeout-us`、`--progress-sec` 等，见 `--help`。

## 7. 运维事项

- **CPU 规划**（4 核无超线程）：核 3 由 `isolcpus/nohz_full/rcu_nocbs` 隔离，runtime 独占；核 0–2 给 OS、SSH、C 和进度上报线程（核 1）。
  实测核 3 在 busy loop 下，来自本机内核的中断每秒只有约 2 次；另有虚拟机宿主机造成的短暂停顿每秒约 200 次（主循环的停顿检测，累计占约 0.06%），这部分隔离不掉。
- **网卡**：device-number 0（SSH 所在）永远留给内核；`bind.sh` 内置保险，拒绝绑定 SSH 所在的网卡。
  `unbind.sh` 可把 DPDK 网卡还给内核。
- **大页**：启动参数预留 1024 × 2 MiB；EAL 使用 `--in-memory`，进程退出后不在 `/dev/hugepages` 留文件。
- **长测期间不要在本机编译**：编译会占满核 0–2 并冲刷与核 3 共享的 L3，污染尾延迟。
- **日志**：直接运行 `run.sh` 会在 `logs/` 下留一对 `.log` + `.json`（随手测试的产物，已被 `.gitignore` 忽略）；
  要留档的运行由 `campaign.sh` / `session.sh` / `ab.sh` / `drift.sh` 写进各自的子目录。`logs/ab-*/summary.txt` 是交替对比的汇总。
- **图**：`scripts/plots.py` 生成 `docs/img/` 下的图，文字用中文（`setup.sh` 会安装 Noto Sans CJK SC 字体）；找不到中文字体时自动退回英文，不会出现乱码。

## 8. 换一块网卡要改哪几行

网卡参数不写死在代码里。`scripts/detect-nic.sh [device-number]` 通过 IMDS + sysfs 自动探测并生成 `config/nic.env`：

```bash
DPDK_PCI=0000:28:00.0      # ← 绑定到 DPDK 的 PCI 地址
DPDK_IFACE=enp40s0         # ← 它在内核里的名字
DPDK_MAC=06:ff:df:7d:66:91 # ← 源 MAC（程序实际使用端口报告的 MAC）
DPDK_IP=10.202.15.133      # ← 源 IP（AWS 源地址检查要求是该 ENI 的 IP）
KERNEL_IFACE=enp39s0       # ← C 使用的内核网卡
PEER_IP=10.202.8.15        # ← 对端
PEER_MAC=06:ff:fd:b6:f0:cd # ← 对端 MAC
```

换网卡 = 先 `scripts/unbind.sh`，再重跑 `scripts/detect-nic.sh <device-number>`（或直接改上面这几行），然后 `scripts/run.sh`。
换成非 ENA 的网卡时，还要在 `scripts/setup.sh` 的 `-Denable_drivers=` 里加上对应的 PMD（比如 `net/mlx5`），并视情况改用 vfio-pci。
